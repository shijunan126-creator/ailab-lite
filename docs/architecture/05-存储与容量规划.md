## 1. Pacific 9950 存储规划

### 1.1 先确认的两件事

1. **99 TB 是裸容量还是可用容量？** Pacific 用 EC 保护数据，8 节点规模下通常是 4+2（67%）到 6+2（75%）。如果 99 TB 是裸容量，可用容量只有 **约 66～74 TB**。下表按两种情况分别给出。
2. **已购买哪些服务许可？** Pacific 按服务类型授权（文件 / 对象 / HDFS / 块），DPC 客户端也可能单独授权。用 `show license` 确认。**本设计假设“文件 + 对象（S3）”都已授权**；如果没有对象授权，见 1.4。

### 1.2 空间分配

| 用途 | 协议 | 规划配额 | 说明 |
|---|---|---|---|
| 模型权重 `/models` | NFS（文件系统 `ai-models`） | **15 TB** | 当前模型（含上一版本和原版）约 2.5～3.5 TB，为迭代和评测留余量（见 02 第 4.4 节） |
| 用户资料库 | S3 桶 `ailab-library`（开版本管理） | **25 TB** | 1000 人 × 20 GB = 20 TB 逻辑上限；实际平均使用率预计 30%～50% |
| 预览与缩略图 | S3（同桶前缀） | 2 TB | |
| 镜像仓库（Harbor） | S3 桶 `ailab-registry` | 2 TB | 沙箱镜像、推理镜像（推理镜像每个约 15～25 GB）、平台镜像 |
| 日志（Loki）、审计归档 | S3 桶 `ailab-logs` | 4 TB | 日志保留 90 天，审计归档 ≥1 年 |
| 数据库备份（CNPG WAL + 全量） | S3 桶 `ailab-backup` | 3 TB | 保留 30 天 PITR |
| K8s 共享卷（CSI，非数据库） | NFS | 2 TB | 少量需要共享文件系统的平台组件 |
| 知识库 / RAG 原始语料（三期） | S3 / NFS | 5 TB | 预留 |
| **合计规划** | | **≈58 TB** | |
| **余量**（性能和扩容） | | **≥25%** | 分布式存储写满后性能会下降，建议使用率不超过 75% |

**结论**：如果 99 TB 是**可用**容量，空间很充裕（规划后余量约 40%）。如果是**裸**容量（可用约 70 TB），规划后余量约 17%，需要把资料库配额收紧到 15 GB，或者推迟 RAG 预留。

### 1.3 访问与隔离

| 客户端 | 访问内容 | 权限 |
|---|---|---|
| 8 台 Atlas | `ai-models/repo` | **只读** NFS |
| 模型入库主机（运维管理机） | `ai-models/staging`、`archive` | 读写 |
| Platform API、Broker、文件处理 Worker | `ailab-library`、`ailab-upload-tmp` | S3 读写（独立 S3 账户，最小权限的桶策略） |
| Harbor | `ailab-registry` | S3 读写 |
| Loki | `ailab-logs` | S3 读写 |
| CNPG | `ailab-backup` | S3 写入（备份）+ 读取（恢复） |
| K8s CSI（Huawei eSDK 4.13，ARM64 包） | 共享卷 | 按 PVC |
| **沙箱** | **任何存储都不能访问** | — |

### 1.4 没有 S3 授权时的降级方案

- 资料库：NFS 文件系统 `ai-library`，**每个用户一个 dtree，设 20 GB 硬配额**（SmartQuota），只挂载到 Platform API 和 Broker 的 Pod（CSI dtree 卷）；预签名下载改为由 Platform API 流式中转。
- Harbor、Loki、备份：改用 NFS 卷。
- **不使用 MinIO**（社区版已停止维护且镜像已下架）。如果确实需要 S3 语义，在 NFS 上部署 SeaweedFS（Apache-2.0）。

### 1.5 不放在 Pacific 上的数据

| 数据 | 位置 | 原因 |
|---|---|---|
| PostgreSQL | TaiShan 本地 NVMe（CNPG 主备各一份） | 数据库不放 NFS；Pacific 9950 不提供块存储 |
| etcd | TaiShan-01/02/03 的本地 SSD（每台一个成员） | 对时延敏感 |
| Valkey | 本地盘（可丢数据） | |
| Prometheus/VictoriaMetrics TSDB | 本地盘 | TSDB 不适合 NFS |
| 沙箱镜像层、沙箱临时盘 | 本地盘（containerd） | 随沙箱销毁 |

> **前提**：三台 TaiShan 需要有 NVMe/SSD 数据盘（建议每台 ≥ 2 × 3.84 TB，RAID1）。请确认实际配置。

## 2. 通算（鲲鹏）容量测算

### 2.1 已知和假设

| 项 | 值 | 状态 |
|---|---|---|
| CPU | 3 台 × 128 核 = **384 核** | 用户提供（2026-10-20 更新为 3 台；假设三台配置相同） |
| 内存 | **按 512 GB/台估算**，另给出 256 GB、768 GB、1 TB 的情况 | **待确认（现在是决定容量的关键参数）** |
| Kata 每沙箱开销 | 250m CPU + 320 MiB（kata-deploy 默认 PodOverhead） | PoC 实测后下调 |
| 沙箱 standard 规格 | request 250m CPU / 2 GiB，limit 2 vCPU / 2 GiB | 本设计；Chromium + LibreOffice 同时运行时内存偏紧，P0 实测后可能调到 3 GiB（容量：256 GB/台约 140，512 GB/台约 375，768 GB 以上约 605） |

### 2.2 平台服务资源预留（三台合计，requests）

| 组件 | 副本 | CPU | 内存 |
|---|---|---|---|
| 系统（kubelet、containerd、Calico、CSI、控制面、etcd） | 每节点 8 核 / 32 GB × 3 | 24 | 96 GB |
| PostgreSQL（CNPG） | 2 | 8 | 64 GB |
| Valkey | 2 | 2 | 16 GB |
| Keycloak | 2 | 2 | 6 GB |
| Higress（网关 + 控制器 + 控制台） | 2 | 4 | 8 GB |
| Portal | 2 | 2 | 4 GB |
| Platform API | 2 | 4 | 8 GB |
| Agent Service | 3 | 6 | 24 GB |
| Sandbox Broker | 2 | 1 | 2 GB |
| 包镜像（PyPI/npm 代理） | 1 | 1 | 4 GB |
| 文件处理 Worker | 2 | 4 | 8 GB |
| OpenSandbox Server、Controller、Ingress | 1～2 | 3 | 6 GB |
| GPUStack Server（含内置 Prometheus、Grafana） | 1 | 4 | 16 GB |
| 可观测性（VictoriaMetrics、Loki、Grafana、Alertmanager） | — | 6 | 32 GB |
| Harbor | 1 | 2 | 8 GB |
| **合计** | | **≈72 核** | **≈298 GB** |

> 系统部分按每节点保留计（kubelet `system-reserved` / `kube-reserved`），其余为 Pod requests。这里取的是偏保守的上限，实际平均使用量会低很多，但**预留必须按上限算**，才能保证平台不被沙箱挤垮。

### 2.3 沙箱容量

可分配给沙箱的资源 = 总量 − 平台预留：

| 每台内存 | 可用 CPU | 可用内存 | 按 CPU 算（0.5 核/个） | 按内存算（2.31 GiB/个） | **正常容量** | **单台故障时** |
|---|---|---|---|---|---|---|
| 256 GB | 312 核 | ~470 GB | 624 | ~205 | **≈205（受内存限制）** | ≈105 |
| **512 GB** | 312 核 | ~1.24 TB | 624 | ~535 | **≈535（受内存限制）** | ≈330 |
| 768 GB | 312 核 | ~2.0 TB | 624 | ~870 | **≈620（受 CPU request 限制）** | ≈380 |
| 1 TB | 312 核 | ~2.77 TB | 624 | ~1200 | **≈620（受 CPU request 限制）** | ≈380 |

> 计算口径：每个标准沙箱调度占用 CPU 0.5 核（request 250m + Kata 开销 250m）、内存 2.31 GiB（2 GiB + 320 MiB），按 GB≈GiB 粗算，取整到 5。

- **每台 128 核时，瓶颈是内存，不是 CPU**：512 GB/台时内存先到上限（约 535 个）；要把 CPU 用满（约 620 个），每台大约需要 600 GB。
- 单台故障时：剩下两台仍能放下所有平台服务的全部副本（两副本服务各占一台，单副本服务漂移过来），平台预留约 64 核、266 GB（只少了一台的系统预留）。512 GB/台时，两台剩下约 192 核、760 GB，按内存还能跑**约 330 个**沙箱，**远高于正常需求（50～100）**。三台通算后，控制面 HA（etcd 三成员各占一台）和容量都不再是短板。
- **超分比的口径**：本文统一定义为 **limit ÷（request + Kata 开销）**，标准规格为 2 ÷ 0.5 = **1:4**（按物理核算：535 个 × 2 vCPU ÷ 312 核 ≈ 3.4 倍）。内存不超分。
- CPU 富余，P0 压测时可以考虑提高 CPU request 换取更稳的性能：**提到 333m（1:3.4）以内**，312 核 ÷ 0.583 ≈ 535 个，沙箱数量基本不变；**提到 500m（1:2.7）**，312 ÷ 0.75 ≈ 415 个，CPU 会取代内存成为瓶颈。
- 设计目标（512 GB/台）：**正常约 535 个、全局软上限 ≈430（80%）、硬上限 ≈510（95%）**（留余量给预热池和突发；实际上限由 Broker 按 allocatable 动态计算，见 03 第 4.2 节）。按 1000 名用户、10% 同时使用 Work 计算，需要约 100 个，**余量很大**；即使 30% 的用户同时使用 Work，也能撑住。

### 2.4 超分的安全阀

1. 沙箱的 `PriorityClass` 最低；节点资源紧张时，kubelet 先驱逐沙箱，平台 Pod 不受影响。
2. 节点内存水位超过 85%，或 CPU 使用率持续 5 分钟超过 85% → Broker 把全局上限临时下调 20%，同时预热池缩到最小。
3. 监控 `container_cpu_cfs_throttled_seconds`（被限流时长）和任务 P95 耗时：如果 P95 劣化超过 30%，把超分比回调到 1:3.4（CPU request 改为 333m）。
4. PoC 压测分档：request 500m（1:2.7）→ 333m（1:3.4）→ 250m（1:4）→ 125m（1:5.3），测出“P95 任务耗时劣化 ≤ 20%”时的最大并发，作为最终参数。

## 3. 智算容量（摘要）

| 模型池 | NPU | 估计并发能力 |
|---|---|---|
| DeepSeek-V4.1-Flash（1P1D：P 16 卡 + D 16 卡） | 32 | 约 64～128 条并发序列，支撑约 50～100 个并发专家档 Work 任务 |
| Qwen3.6-35B-A3B（TP2 × 10） | 20 | 数百个并发 Chat 流 |
| Qwen3.8-27B（TP2 × 4） | 8 | 约 100～200 条并发序列（标准档 Work、子 Agent、降级兜底） |
| OCR / 向量 / 重排 | 4 | 文档解析与检索 |

> 这些都是量级估算，**以 P0 阶段 AISBench 压测为准**，并据此设定网关限流和平台准入。

## 4. 扩容建议（按优先级）

1. **内存配到 ≥512 GB/台**：每台 128 核时，内存是沙箱容量的唯一瓶颈；约 600 GB/台时 CPU 和内存基本平衡（约 620 个）。按 50～100 个的需求，256 GB/台（约 205 个）也够用，但单台故障时只剩约 105 个，余量偏小。
2. **运维管理机（可选）**：三台通算后 etcd 不再需要第三台机器；堡垒机、出网代理、模型入库主机可以用公司现有的运维机或 VM。
3. **利用 Atlas 的空闲 CPU（远期选项，有条件）**：每台 Atlas 800T A2 有 4 颗鲲鹏 920（192～256 核）和 TB 级内存，推理只用其中一小部分。理论上可以把部分 Atlas 节点加入 K8s 作为沙箱节点，但需要：① 用 cpuset 和 NUMA 隔离，避免干扰 vLLM 的 CPU 绑核；② 安全评审（不可信代码和 NPU 服务在同一台物理机上）；③ 解决 Docker（GPUStack）和 K8s 两套容器运行时共存的问题。**第一期不做**；现有三台 TaiShan 已能支撑数百并发，近期也不需要。
