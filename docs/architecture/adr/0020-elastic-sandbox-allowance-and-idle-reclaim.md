# ADR 0020 · 弹性沙箱额度与闲置回收

状态：采用（2026-10-26）。修订 [ADR 0003](0003-broker-exec-proxy-and-leases.md) 的 `sandbox_max_per_user=1` 与“用户满了只排队”；与 [03 第 4 节](../03-Agent与沙箱设计.md) 的 LRU 策略一致，但不含部门份额与软/硬水位。

## 背景

每人固定 1 个沙箱时，用户并行两个任务（两个会话各一个 Run）必有一个排队，而此时池子往往是空的。固定上限也没有“谁该让位”的规则：满了就一律排队，闲置的沙箱要等 TTL 才释放。

## 决定

**弹性额度。** 每人第一个沙箱按容量正常放行；第 2 个及以后（上限 `sandbox_max_per_user`，默认 3）只在“放行后通用池占用率（槽位与内存取大）不超过 `sandbox_burst_watermark`（0.8）”时放行，否则有效上限回到 1。已有的沙箱不因水位变化被杀。渲染池不参与。

**闲置回收。** 一个 Run 被排队挡住，原因是“用户到有效上限”或“池满”时，Broker 才找可让出的沙箱；每 2 秒重试一次：
- 候选必须 `active`、不是渲染、没有进行中的操作，且距最后一次操作至少 `sandbox_evict_idle_seconds`（300）。未满 5 分钟的一律不动，两个忙的 Run 因此不会互相驱逐。
- 用户上限：只回收该用户自己的，最久无操作者先走。
- 池满：全用户可选，但通用池占用率须 ≥ `sandbox_preempt_utilization`（0.95）；沙箱最多的用户先让一个（先动爆发额度），其次最久无操作。
- 一次只回收一个：上一个还在保存或删除时不再选下一个。

“操作”只指 Agent 对租约的调用（exec、读写文件、列目录、交付、预览、快照、取消 exec）。续租、状态查询、释放不算，否则每个 Run 的心跳都会让沙箱看起来很忙。活动时间只在 Broker 进程内存里记录（单 Broker 持有全部租约；每条命令写一次 Redis 会与续租争同一条记录的版本）；Broker 重启后所有租约重新计时。

**先保存再删除。** 被选中的租约先置为 `releasing`（原因 `evicted_idle`，调用方立刻得到 410，对账暂不删除），Broker 自己打工作区快照，写入租约的 `eviction_snapshot`，再删除资源。快照失败也释放槽位，Run 退回自己最近一次防抖快照并被告知“工作区可能落后”。

**Agent 侧。** 收到 410 的 Run 沿用既有的“租约中断”路径，但先向 Broker 取回 `eviction_snapshot`（最多等 240 秒）写进检查点，清空后台命令记录、追加平台提示，然后 `INTERRUPTED` + 自动续跑。回收造成的续跑使用独立计数 `evict_resumes`（最多 3 次，用户手动继续或回答问题后清零），不占故障自动续跑的那 1 次。

## 后果

- 当前本机池只有 1 个工作槽位，行为与此前相同；规则在集群容量下才放开。
- 后台命令（`exec` 后台任务）随沙箱终止，Run 会被告知需要重启。Broker 不知道哪些后台命令还在跑；模型在等后台命令时通常在轮询（算操作），安静超过 5 分钟的情况才会被回收。
- 排队等待 300 秒，与 5 分钟保护期几乎相等：刚好都忙的请求可能超时，由 Agent 现有的 429 重试处理。
- 未做：按角色的不同上限、部门份额、软/硬水位分级、预热池。`sandbox_max_per_user` 目前对所有人一样。
- 验证边界：单元与契约测试用 mock provider；真实 Docker/OpenSandbox 下的回收与快照、多并发 Run 的端到端行为未验。
