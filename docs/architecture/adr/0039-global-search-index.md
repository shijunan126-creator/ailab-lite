# ADR 0039：全量对话搜索用会话级词项索引

- 状态：已实施（2026-11-11，分支 `feat/search-index`，base `origin/main@01c1d16a`）
- 相关：[搜索性能记录](../../progress/updates/2026-11-11-search-index.md)、[基准脚本](../../../platform/scripts/bench_search.py)

## 背景

原来的 `/v1/search` 每页只访问 50 个会话、检查最多 1000 个 Run，命中不足就返回 `next_cursor`；Portal 最多自动续查 6 页，然后显示“继续搜索”。这有两个问题：

1. **搜不全**：较早的命中可能落在 6 页之外，用户看到“没有找到”或必须手动继续；旧前端无法在一次查询里搜完整个账号。
2. **搜不快**：要证明“没有命中”就必须把每个会话的每个 Run 的 prompt/summary 都做一次 `lower(...) LIKE`。数据量线性增长，且 N+1 查询。

目标是一次请求搜完整个账号，并且在很多对话、很多轮次下仍然快、准。

## 决定

每个会话一行 `conversation_search`，保存它出现过的所有可搜索词项的**并集**；数据库对这份并集建索引：

- SQLite：FTS5 虚拟表（external content + 触发器）。
- PostgreSQL：`terms_tsv` 存储列（触发器从 `terms` 生成 `to_tsvector('simple', ...)`）+ GIN 索引。

查询先用索引选出候选会话，再只扫描这些候选会话的 Run，找到最新的一条精确命中。没有游标，没有“继续搜索”。

### 词项与匹配

- 归一化：NFKC + casefold，索引和查询使用同一套规则。
- 拉丁文/数字：整词，以及按 `_ . - /` 拆出的部分（`ailab_platform` 同时产生 `ailab_platform`、`ailab`、`platform`）。
- CJK：连续汉字的全部 bigram（`机器学习` → `机器`、`器学`、`学习`）。
- 查询按空白切成多个 segment；每个 segment 都必须出现在同一个 Run 的 prompt 或 answer 中（可以一个在问题、一个在回答里）。这比旧的“整段 query 作为一个字面子串”更符合多关键词搜索。
- 候选过滤使用 query 词项的一个子集（最多 48 个，均匀采样）。真命中一定包含全部词项，所以子集只会多召回、不会漏召回；最终仍由 SQL `LIKE` + Python 校验确认。
- 排序沿用旧行为：按会话 `updated_at` 新到旧；同一会话内标题命中优先于正文命中，prompt 优先于 answer。标题和正文一起参与候选，标题命中不需要再扫 Run。

### 索引维护

- 会话标题、Run prompt、Run summary 的 ORM 写入在同一个 `before_flush` 里把新词项并入会话行；`run_state` 的 compare-and-set 更新显式调用同一个函数。
- 并集**只增不减**：编辑、重试、删除 Run 或改标题留下的旧词项只会让候选多一次校验扫描，不会隐藏真实命中。删除会话时外键级联删除索引行，SQLite 的 FTS 触发器同步删除。
- 迁移 0070 只建表/索引，不回填。启动后的后台任务按 `(updated_at, id)` 水位分批把旧数据并进索引；ORM 路径已经即时写入，水位任务只是补齐旧库和兜底。

### 单字查询

一个字符（或纯标点）产生不了可用的索引词项，走有界回退：按会话新到旧检查最多 200 个会话。这是唯一不覆盖整个账号的输入；正常的两字及以上查询都走索引。UI 在输入为空时显示最近对话，单个字符仍会请求后端，由后端做有界回退。

## 备选方案

- **每个 Run 一行 FTS/GIN**：写入更简单，但同一会话的重复词项无法去重，索引体积约为会话级的数倍；查询还要先按会话聚合。放弃。
- **关系型 `(term, conversation_id)` 倒排表**：两个数据库都能用普通 B-tree，但行数按“会话 × 不同词项”增长，100k Run 量级会达到数千万行。放弃。
- **PostgreSQL `pg_trgm` / SQLite trigram**：需要额外扩展或只支持 3 字符以上，且两库语义不一致。放弃。
- **进程内索引**：API 只有 256–384 MiB，索引体积会挤掉请求处理；重启还要重建。放弃。

## 代价与边界

- 索引体积：SQLite 实测约为原文的 9 倍（100k Run / 120 MB 文本 → 1.07 GB 数据库）；PostgreSQL 因为有 `terms_tsv` 存储列，2000 会话 / 24 MB 文本约 98 MB。40 GiB 的 lite 数据卷可容纳，但这是明确的磁盘成本。
- 首次升级已有大库时，后台回填完成前旧会话可能暂时搜不到；新写入不受影响。回填在后台分批执行，不阻塞 API。
- 拉丁文按词匹配，不做任意子串匹配（`search` 不命中 `searching`）；中文 bigram 保持字面子串。这是本 ADR 明确接受的精度边界。
- 旧词项不删除会随编辑次数增长；候选扫描有 2000 个会话的预算。极端频繁编辑后若候选质量下降，应增加一次重建索引的维护任务，而不是放宽预算。
