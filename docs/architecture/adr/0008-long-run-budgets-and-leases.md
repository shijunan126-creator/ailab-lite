# ADR 0008 · Long Run budgets and renewable ownership

Status: implemented locally (2026-10-25); extends [ADR 0004](0004-self-developed-runtime.md). Validation and remaining boundaries: [long Runs](../../progress/updates/2026-10-25-long-runs.md).

## Decision

Cost, liveness and useful working time have separate bounds. Keep the cumulative 2M raw-token Run ceiling and user weighted quota; increase the step runaway backstop to 300 per continuation. A long task does not get an unrestricted spending allowance. 2M supports at most about 6,667 average prompt+completion tokens over 300 calls, less when reviews/summaries/retries consume calls. 300 is a safety ceiling, not a promise to fund 300 full context windows. Current-Run context compaction at 65% of model input capacity complements historical-turn compaction; summary inference is metered normally. Preserve the original input and two complete recent assistant/tool groups; the execution log and plan remain authoritative.

A Run job has a 300-second claim. The Agent renews it every min(60, lease/3) seconds through service-scoped, token-and-expiry-fenced POST `/internal/jobs/{id}/renew`. Renewal updates the same indexed outbox row and its dispatch eligibility. It cannot resurrect expired ownership. Any renewal failure cancels current work, retains the durable job and relies on recovery. Queue visibility uses the lease duration; production execution uses the durable claim rather than a second duration lock. Transport duplicates during long work are harmless; the durable dispatcher republishes an expired claim at its next tick. Recovery is approximately one lease plus dispatcher cadence, independent of Run age. A continuation always has a new job identity.

The checkpoint stores monotonic active seconds, review threshold, start step and measurable-progress baseline under that job identity. Crash recovery preserves this window; manual resume/answer creates a fresh time/step window. Sandbox admission waits are excluded; waiting_user/interrupted do not hold an executing Agent. Crash downtime is not charged to active work; time since the last persisted checkpoint can be undercounted. `work_ms` remains the existing user-visible cumulative RUNNING timer (including admission); it is not reset by continuation.

After 1h active work, the model receives a self-review note. A new completed/skipped plan ID or distinct written/delivered file allows a 30-minute extension. Text, polling, plan oscillation and repeat delivery do not. Without new progress, send a wrap-up note and allow up to three further model steps. At 4h, do the same even if progress continues. Thus the time ceiling begins bounded graceful wind-down at a step boundary; it is not a mid-call execution kill. Up to three model steps and bounded tool/finalization calls can exceed the threshold. The 300-step backstop adds one tools-disabled summary call. Then stop tracked background jobs, deliver leftovers, force a workspace snapshot/checkpoint and pause as interrupted without auto-resume. A 20-minute lack of successful event/model/tool progress cancels the await and takes the same pause path. Model calls keep their own deadlines; commands/waits remain at most 600 seconds. Config requires the stall interval to exceed these single-call bounds.

Budget pauses are not FAILED. Real execution/configuration failures retain FAILED. Cumulative token exhaustion also pauses, but the resume endpoint rejects another same-Run attempt when its token ceiling is exhausted; the user must start a new task subject to quota. Time/step pauses can repeat without a fixed continuation count while cumulative tokens, user quotas, admission and checkpoint retention permit it. No pause automatically resets cost.

`exec(background=true)` uses the existing Broker exec privilege to start a detached stdlib Python supervisor inside the sandbox. `exec_wait` reads bounded incremental output and exit state; `exec_kill` kills the process group and is idempotent while the handle is retained. Start is the existing non-replayable `exec`; wait/kill may replay. Control data/logs live in `/tmp/ailab-background`, outside workspace snapshots. A restored sandbox cannot revive old handles or signal a recycled PID (Linux /proc process-start identity fence). Missing handles explicitly require inspecting saved files before deciding to restart. Completed handles may be evicted on a subsequent start to bound disk. Four jobs and 1MiB ring log each are default ceilings; output is continuously drained, not buffered without limit. Controls return at most 4KB output. Supervisors have a bounded lifetime. Pauses and completion stop known jobs before the final snapshot; lease release destroys remaining sandbox processes.

## Cost and boundaries

No schema migration, new service or package dependency. Default claim renewal is one indexed single-row UPDATE per minute per executing Run, plus the existing sandbox renewal/status polling. WorkBudget bookkeeping is O(1) per boundary; existing checkpoint objects include a small clock/progress record. Background supervision uses one small Python process per active command, at most four, plus the command's own CPU/RSS inside the existing sandbox limit; log disk is at most 4MiB by default. Host measurements and unverified Linux/provider boundaries are in the validation record. Progress is a heuristic based on recorded state, not semantic proof that the generated files are useful.
