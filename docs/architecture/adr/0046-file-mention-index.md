# ADR 0046：输入框文件名联想采用倒排索引

状态：已采纳。

## 背景

输入框每次按键都可能查询资料库和历史交付件。即使只返回 8 条结果，`LIKE '%片段%'` 也要访问账号下的大量文件，越罕见的输入越难提前结束。账号有 10 万个文件时，联想需要索引定位候选，并在有限范围内核对文件名与可见性。

## 决定

- `file_search` 按血脉存一行，仅索引可用的资料库 head。SQLite 用触发器同步 FTS5 external content 表，为常用的短前缀建索引。PostgreSQL 用触发器维护 `tsvector` 存储列及 GIN 索引。词项包含账号标记，候选和返回结果同时校验归属与隔离规则。
- 文件名与查询使用 NFKC 和 casefold。保留拉丁标识符全词，并按大小写、数字与字母、分隔符拆出子词。CJK 同时存单字和 bigram，单字支持第一键联想，bigram 缩小多字候选。Python 校验连续命中并把高亮还原到原始文件名的码点。
- 仅最后一个拉丁片段按词首前缀查找，其余拉丁片段按整词，所有片段都须命中。SQLite 用 `MATERIALIZED` 让 FTS 驱动取候选，PostgreSQL 的全库候选先完成 GIN 匹配再排序。先在近期词项行的窄窗口尝试取满 200 个候选，按真实时间与 ID 校验窗口边界。窗口不足或索引行号不够集中时，全索引仍可找到旧文件。
- 单独取当前对话的最近 50 个可用 head。任一 Run 的附件或交付均按原文件 ID 定位血脉，命中后按当前 head 返回。候选不足时，只在最近 2000 个可见文件中补词中片段，补位使用最低匹配档。
- 就绪、改名、项目移动、换版、恢复与清除在文件事务内维护索引。迁移建立结构，API 在启动后按账号、创建时间与 ID 水位，每批最多 200 行补旧数据。回填期间，新写入即时可搜，旧文件随回填逐步进入全文候选。

## 代价与边界

- [基准脚本](../../../platform/scripts/bench_file_mentions.py) 使用一个 10 万文件账号、2.5 万个其他账号文件和一段 12 轮对话。Apple M1 的 SQLite 3.50 与 PostgreSQL 16 均以每类 40 次测量。六类查询最慢的 p95 分别是 19.88 ms 和 21.50 ms。
- 同一合成库中，SQLite 全文结构约 66.76 MiB，文件近期索引约 24.98 MiB。PostgreSQL 分别约 100.14 MiB 与 26.06 MiB。两库建立结构分别约 0.64 秒和 0.36 秒，批量建全文词项分别约 10.90 秒和 8.49 秒。后台回填还受批次间隔和并发写入影响。
- 200 个全文候选按时间截取，排序档位在候选内计算。词中补位限于近期文件且只在结果未满时运行。历史任意子串与大量同词结果中的更早文件不保证召回。
