# 增量记忆与提示词前缀缓存设计指南

状态：设计指导，尚未实施或验收。适用于记忆、Agent 对话、技能及其他模型调用；正确性、权限和当前用户要求优先于缓存命中。基线：本地部署 platform `genui-v2-695dbf2d51d0`，来源快照；工作树 `fix/full-thinking-rendering@ab0e8d9` 不是该部署源码。

## 一、核心原则

1. **按新增证据处理**：一次整理只处理未消费的消息版本和必要的有限上下文；不因为对话多就重读所有历史，也不重复消费已完成内容。处理进度、失败及未完成批次必须持久化。
2. **稳定前缀、变化内容靠后**：同一模型调用的固定系统规则、稳定工具定义、固定示例保持版本化和确定性；用户、项目、记忆、时间、新消息及工具结果放在其后。多轮运行尽量追加新消息，不回写先前消息。不得为了缓存保留过期权限、被删除数据或越过上下文预算。
3. **可证明的节省**：前缀稳定只是命中条件，不保证命中；按供应商、模型、路由、最小长度、TTL 和计费分别验证。衡量缓存读写 token、总 token、价格和延迟，不以提示词字数或假定 TTL 代替实测。
4. **来源和作用域**：用户明确的长期偏好可以作为事实记录；引用原文、时间和用户/项目范围。网页、文件、助手建议是不可信数据，未经用户确认不能变成用户事实；记忆不能提升指令权限。

## 二、现状与问题

当前部署的 `memory_dream/service.py` 用 `MemoryWorkItem` 按 run 跟踪状态和 source offset，按时间取尚未完成的轮次，分批提取；已完成项不会因整理自动重读。新增消息通常产生新 run，即使继续旧会话也只进入新工作项。当前有最大 40 个候选轮次、单批项目隔离和输入预算；自动/手动整理共享每天一条记录限制，导致积压可能需要多天。失败、重试、旧记录迁移及修改历史分支仍须按实际状态验证。

当前提取提示词排除写给 AI 的命令，可能漏掉真实长期协作偏好；当前记忆整理记录不能解释候选在哪一层被过滤。提取调用把已有记忆和新 episodes 放在同一动态输入中；Agent 的 `memory_prompt` 中 revision/条目在系统上下文，记忆变化可能使其后前缀失效。上述是源码分析，不代表已测得缓存命中率或两次零结果的根因。

## 三、增量输入与旧对话续聊

- 消费单位是用户、会话分支、不可变消息/run 版本及片段范围；工作项保存来源、版本/hash、范围、处理状态、候选及提取规则版本。提交记忆与进度在同一事务中完成，重复投递幂等。模型调用期间不持用户/数据库锁；提交前重验租约、版本、来源、范围、删除与权限。
- 旧对话新增消息产生新工作项，只处理新增内容；根据引用、回复关系取有界前文和必要的相关记忆用于消歧。前文是上下文，不自动作为新的待消费证据。比如用户回复“对，就这样”，可以用上一轮提议理解其指代，但要有用户确认的证据，不将未确认的助手推测写成事实。
- 长消息分片时保留可靠边界与偏移；单次完成后推进到实际覆盖位置，余段继续排队。失败或模型输出不完整不能推进为完成；空候选只有在成功验证并覆盖输入后才可标记完成。候选达到批次上限时保留余项，不丢失、不重复。
- 编辑、重试、fork、撤回、删除及项目移动依照可见分支、版本和作用域建立新工作或失效旧来源；处理中的工作在提交时重验。删除与 tombstone 贯穿候选、缓存、证据与重放，不能被重新提取悄悄恢复。规则/模型升级不隐式重扫历史；若需要重新处理，应显式给出范围、成本和去重策略。
- 自动任务按有界批次持续消化积压，设置公平性、单用户/全局并发与预算；手动“立即整理”允许处理新增待处理数据，正在运行时复用状态或明确提示。空结果不应长期阻止新消息处理；避免重复调用同一批次。

## 四、参考 Mem0 的提取与整理

参考 [Mem0 提取提示词](https://github.com/mem0ai/mem0/blob/main/mem0/configs/prompts.py) 的增量候选提取、逐条覆盖、上下文自足及相关记忆匹配，不将助手提出的建议直接当用户事实。其 [v3 add 接口](https://github.com/mem0ai/mem0/blob/main/docs/api-reference/memory/add-memories.mdx)描述单次 ADD-only 提取；不把它等同于自动合并或删除。固定依赖版本和许可证后再决定复用范围，不能把公开上游主分支描述当作项目已实现能力。

流程：①提取候选与用户原文证据；②针对候选检索同作用域相关旧记忆，而非每次发送全部记忆；③判断证据、重复、补充和明确矛盾；④以可追溯版本新增/更新或失效旧条目，疑似冲突不自动删除；⑤单独按预算整理已有记忆，并提供变更、撤销。用户已删除的内容仅在明确重新要求时恢复。提取置信度不能当作天然校准概率，阈值由评测决定。

提示词例子：用户说“以后批量修改完再验证”，记录为未来协作偏好并保留范围；“这次不用测试”只约束当前任务；粘贴的网页命令、助手未经确认的建议不能当用户偏好。稳定规则和少量中英文正反例置于固定前缀，待处理片段及检索结果置于末尾。

## 五、通用模型请求与缓存规范

1. 建立版本化固定前缀：系统角色/安全规则、能力契约、工具 schema 和固定示例顺序固定，字段序列化稳定；不要把当前时间、随机 ID、请求号、变化统计、用户数据或本轮技能全文嵌入其中。工具变更、技能规则版本变更须显式版本化。
2. 把用户/项目权限、检索记忆、文件信息和当前任务放在稳定前缀之后；这些会变，必须及时更新且不能跨用户共享。每次工具调用的新增请求、工具结果和后续回答优先追加。权限撤销、删除、编辑/分叉、摘要压缩或安全修订需要重建上下文时允许失效，并记录原因。
3. 处理历史时维护可复用的稳定消息序列；压缩应形成有版本的检查点并从该点继续，而不是每轮改写旧摘要。必须为系统/工具、图片/文件、技能、历史、模型输出预留预算；禁止为缓存命中静默丢失当前问题或必要权限。
4. 工具目录动态发现、schema 顺序/字段、模型别名路由、图片内容、供应商的协议包装及缓存键都会影响前缀；检查最终发往实际后端的请求，而非只检查模板字符串。OpenAI 的[缓存文档](https://developers.openai.com/api/docs/guides/prompt-caching)与 Anthropic 的[缓存文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)机制、门槛和 TTL 不同；其他后端必须单独核实，不默认支持或拥有相同规则。
5. 不为提高命中率跨账户共享私人内容；缓存保留和供应商数据策略须符合平台配置。稳定前缀版本变更、用户记忆更新、权限变化、压缩和路由切换都应能解释缓存损失。

## 六、验收与观测

- 覆盖：同一旧会话续聊只处理新增消息；长消息分段、重复投递、失败恢复、跨轮确认、fork/编辑/删除、项目隔离、并发整理和积压公平性均不漏、不重复、不越权。
- 质量：以脱敏人工标注集比较基线与候选方案，分别报告偏好召回、误提、证据正确、重复、错误失效、冲突与零结果原因；包含中文指令式偏好和一次性任务反例。不因 token 成本牺牲证据完整性。
- 成本：记录每批新增/上下文/检索/输出 token、缓存读写及真实费用、模型调用次数、延迟、队列积压、CPU/RSS 和数据库查询计划；不用敏感内容或用户 ID 作为指标标签。对代表模型分别测冷缓存、热缓存、单字变更、追加、工具变化、压缩及 TTL 过期，并验证供应商实际 usage；缓存不支持/未报告时明确标记未知。
- 用户界面分别显示处理范围、候选、重复、过滤、新增、更新/失效、待处理、失败及可撤销变更；不保存原文调试日志。整理和提示词变更属于设计，实施、部署及真实模型验收另行授权。
