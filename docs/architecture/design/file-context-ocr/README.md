## 本轮已明确的设计方向

- **Chat**：先把常见文档预处理成可直接理解的结构化文字；通过整轮预算后再送模型，快速回答。超出Chat能力的文档明确拒绝本轮附件使用，提供切Work/选范围，不能截掉大半后假装全文。
- **Work**：给原文件、必要元数据和处理能力索引，不默认灌入全文；Agent按需发现工具、加载skill，选择解析库、选页渲染、直接看图或平台OCR。可复用Chat/资料库已有处理结果。
- **图片**：两模式的视觉模型直接看；非视觉模型自动用专用OCR转文字，明确这不提供图像语义。模型菜单显示视觉icon，仅在有图片且不支持视觉时显示一次短提示。
- **OCR**：采用RapidOCR集成路线，**昇腾NPU优先**；优先验证RapidOCR＋ONNX Runtime CANN EP，固定PaddleOCR来源的模型。CPU是开发/显式启用的备用配置，不是本架构首选，也不得在NPU失效时静默回落。
- **省token**：正文、图片、工具schema和skill说明全部有预算；只加载相关能力，不依赖200K窗口。先按8K/16K/32K模型验证再扩展。

## 跨模块不变式

1. 原文件按FileObject精确版本保存；原文、派生物、消息引用和模型输入分离。mode只是读取策略，不产生第二份原文件。
2. 文件与哪条用户消息关联由程序记录；自然语言指代只能缩小候选，不能提供越权访问或保证任意歧义都能解。
3. Chat预处理和Work按需工具读取共享相同派生物/缓存身份，不建立两套互相不认的OCR结果。
4. 模型自主性服从确定的权限、页/图/token/资源限额；skill文字不等于硬限制。
5. 输入框每轮最多附加5张独立图片，后续轮次可继续附加；该数量不限制历史图片、文档页面/裁剪或单次模型请求。后者按所选模型实际图像能力、token/像素/字节预算决定批次。文档不默认整份渲染后全部送入上下文，任务需要时允许逐批完整处理。
6. READY文件不代表Chat预处理完成；预处理partial不能冒充全文ready。上下文、工具schema、输出预留统一计预算。
7. 摘要是有损背景，精确引用回查来源；文件ID/版本、消费边界、已确认副作用由程序保存。
8. 删除先阻断访问/在途提交，再异步有界清理对象与派生DB内容；回收站和彻底删除是两种不同用户动作。
9. NPU可用、OCR速度和多代摘要质量都要真实证据；“源码有支持”不是目标环境验收。

## 上游复用与技能归属

用户最新要求优先复用ZCode Office Runtime读取核心和对应skills；具体文件路径、依赖/许可与对照计划统一见[09](09-upstream-reuse.md)。这类技能由平台内置、模型按需加载，不进入用户技能页/市场/开关，不是让用户安装插件。平台内部能力已接线；真实外部验收边界见实施记录。

## 本轮取舍状态

用户已明确上述产品分工、RapidOCR路线及NPU优先。尚待测定：目标卡型/分配方式、驱动/CANN/ORT/模型版本组合、并发与延迟；大小/token/页数候选门槛需样本验证；OCR只计量、不计费、不设用户累计配额。五业务服务边界沿用仓库规范；智算执行器在既有模型基础设施承载，不把OCR权重装入每个用户沙箱。

Chat不以执行多轮办公工具为主，但仍可用少量原有搜索/历史读取工具。对于没有tools能力的文本模型，首次文档输入和非视觉图片OCR均由平台准备，不能假定模型会调用工具救场。
