# 技能、办公能力、记忆与轻量计算需求

状态：讨论形成的产品需求，尚未实施或验收；本文件不授权部署。现状基于本机部署来源快照的代码核对，不代表各组件均来自同一个 Git 提交。实施前重新核对目标基线与已有功能，保留用户数据及未提交修改。

## 1. 目标与现状

用户无需安装技能即可使用通用办公能力；可导入、启用和选择多个技能来增加工作方法或风格。Chat 和 Work 可使用同一份技能，具体执行能力由模式提供的工具决定。技能按需加载，记忆按增量处理，模型调用遵守[增量记忆与前缀缓存设计指南](2026-10-30-incremental-memory-prompt-cache-guide.md)。

当前有两套不同能力：ZCode Office Runtime 及其适配的四种平台内部读取指导，和技能页面/广场中的 PPTX、XLSX、DOCX、PDF 技能。前者支持办公文件读取；后者包含制作、处理脚本与指导。目前 PPTX/XLSX 是可开关内置技能，DOCX/PDF 是广场安装的个人技能。自动技能 `auto-skill` 用于提取个人技能，与办公技能不同。

当前手动选择技能是单选，会强制 Work 并将技能全文注入初始提示词；模型也可自行多次加载技能。Chat 有平台文件读取能力，但不提供 Work 沙箱。当前部署 Work 通常在需要沙箱工具时才申请沙箱，恢复工作区等场景也可能提前申请。

## 2. 平台基础办公技能

- 将 PDF、Word、Excel、PPT 的通用读取与操作能力整理为四个**平台内置、不可关闭、无需安装**的基础技能。保留平台文件身份、权限、OCR 和 ZCode 读取路径，以及 Work `office-read`、现有办公库和渲染工具的职责边界。
- 四个技能分别覆盖相应格式的读取、定位与常见处理；例如 PDF 合并、拆分、文本提取，Word/Excel/PPT 的生成、编辑及检查。这是平台整体的能力范围，不是每种模式都能执行全部操作：Chat 使用平台读取工具，Work 才能按需使用沙箱创建、修改和交付文件。
- 系统提示词只给出简短规则：处理办公文件时按需发现并加载相关基础技能；不把四份全文每轮注入。平台应确保必需技能被加载，失败须可见，不能假定模型一定自行搜索到。
- 合并现有 PDF、Word、Excel 通用流程和配套脚本后，评估并移除重复的可选入口。PPT 的通用功能纳入基础技能；演示逻辑、版式及视觉指导作为可选增强技能保留。迁移前逐项核对脚本、模板、素材、授权和功能覆盖；不删用户已安装或修改的副本，不破坏旧版本、引用及名称解析。
- 用户不能关闭基础技能；用户可选技能可以关闭，关闭后不影响基础能力。平台内部读取与用户技能的名称、权限和来源应可区分，避免同名覆盖。

## 3. 技能发现、指定与加载

- 已启用的用户技能可由模型自动发现，再按需调用 `load_skill`；用户可安装广场技能或导入现有技能包。未安装或已关闭的用户技能不能被当作可用技能。
- 用户可以在同一消息手动指定多个技能。平台在初始上下文传递选中技能身份及“必须加载”的要求；不预注入技能全文。执行任务前通过统一加载机制逐个加载，失败、停用、无权限或版本失效时明确反馈，不能悄悄忽略。加载后仍允许模型发现其他相关技能。
- 同一技能可包含文字规范、脚本与资料。用户导入的技能无需为 AILab 改写或添加 Chat/Work 标记；模型根据实际工具使用适用部分。用户当前明确要求优先于旧偏好；可选技能不能扩大权限或覆盖平台安全及文件权限。
- Chat 和 Work 都能使用纯文字技能。手动指定技能不自动切换 Work；Chat 可读取技能与平台文件，不提供沙箱执行和沙箱产物交付。Work 才能按需运行脚本。用户要求当前模式无法完成的实际操作时，说明需要 Work，不把写出代码当成已执行。

### 办公任务的模式边界

| 用户任务 | Chat | Work |
| --- | --- | --- |
| 读取、检索、总结或引用 PDF/Word/Excel/PPT | 调用平台文件读取及可用视觉/OCR工具，按需加载对应基础技能的读取指导 | 可同样使用平台读取工具；工作区文件还可按需使用 `office-read` |
| 起草报告、表格内容或给出脚本 | 可直接在对话中输出文字、表格或代码；不声称已经执行 | 可直接回答，也可按任务使用工具 |
| 合并/拆分 PDF，生成或编辑实际办公文件 | 不运行沙箱，不声称已创建或交付文件；用户确需文件时说明需要 Work | 按需启动沙箱，使用基础技能及办公工具处理、检查并交付 |

四个基础技能为跨模式的能力组织，加载技能说明不等于获得该技能涉及的全部工具。模型在 Chat 加载含脚本步骤的技能时，只能执行当前工具允许的部分；技能文本不能授权使用不存在的沙箱工具。设计时应避免让 Chat 的能力发现或提示词暗示它能实际执行办公文件写入操作，同时保留用户原样导入技能的兼容性。

## 4. `/` 多技能输入与平台专属交互

- 在句首或空白字符后输入 `/` 打开技能列表，继续输入按名称筛选；技能可以插入句首、句中或句尾。一条消息可引用多个技能。`A/B`、URL 和路径里的斜杠保持普通文本；没有匹配时保留原文、可关闭列表、可正常发送，只有明确选中才插入技能。
- 所选技能以彩色、小型气泡显示，**只显示名称**，不显示描述，不预填任务问题或正文。气泡是可删除、可撤销的独立对象；光标、输入法、复制粘贴和编辑消息均保持文字与技能的顺序。发送时传递稳定技能身份而非仅靠展示名称解析；同名、失效、关闭及重复选择有明确处理。
- 手机技能列表优先利用宽度、允许名称换行；气泡随正文换行，超长名称有最大宽度及触屏可查看完整名称的方式。桌面和手机均能辨认名称，不以固定窄框截断为常态。必要的可访问名称和操作保留。
- 用户导入的技能和无定制的普通平台技能只提供气泡及技能内容，不能注入自定义前端。平台可为少数明确登记的内置功能提供额外交互，例如通过加号或 `/` 选择 PPT 后提供模板选择；模板是关联本轮的独立配置，不是预填正文。多技能情况下确保配置归属、移除和发送一致。

## 5. 提取与编辑技能

- 对话的「提取技能」入口直观可见；分析在后台进行，显示进度且不阻塞用户继续操作。可离开后回来查看状态；失败明确并可重试。
- 先展示技能草稿，用户可查看、编辑、添加或删除草稿文件、放弃草稿，或确认添加/完成。确认前不新增或覆盖正式技能；更新已有技能时展示新增、修改、删除，确认后创建新版本并防止覆盖并发修改。保存后走既有扫描和审核，显示可用状态。
- 技能可为单个 `SKILL.md` 或包含脚本、参考资料和素材的多层目录。预览与编辑应展示目录树、查看/编辑文本、增删改名文件及目录；图片等文件支持预览或上传替换，不支持在线编辑的文件保留原样并可下载。保存完整包，不能因修改说明丢失其他文件。
- 个人 Markdown 技能已有网页编辑能力；当前 ZIP 需下载修改后整包上传，目录级网页编辑是新增需求。平台基础技能由平台维护，不允许用户覆盖；可另存为个人技能定制。

## 6. 对话回到底部

用户向上滚动离开底部时显示半透明圆形向下按钮；点击平滑回到底部，恢复跟随新内容。用户主动浏览历史时不强制拉回；已在底部时隐藏。兼顾手机、桌面、遮挡和减少动态效果的系统设置。

## 7. 浏览器端轻量 JavaScript 工具

- Chat 和 Work 按需发现和调用浏览器端 QuickJS，用于小规模数学、JSON、字符串、正则、数组/对象、CSV 文本转换、过滤、排序、聚合及简单算法或用户小脚本。它是工具能力，不把教程或所有脚本每轮注入提示词，也不要求模型普通回答时生成代码。
- 使用浏览器 Web Worker 中的 QuickJS/Wasm，按需加载；默认不暴露网络、文件系统、页面和宿主对象。明确限制执行时间、内存、栈、输入输出和并发；引擎中断加 Worker 外层超时兜底，失败可解释、不会阻塞 UI 或无限重试。
- 服务端模型调用需经有身份绑定的客户端执行请求/结果回传，明确请求归属、超时、取消、去重及结果可信边界。断线、关闭页面、多标签、后台任务和无在线浏览器时不得无限等待或伪称成功；不可用时明确报告，是否提供替代执行路径另行设计。
- 下载体积、冷/热启动、耗时、内存峰值、手机响应及循环/正则/大输入超时需实测；不得以第三方包体积当作实际性能或承诺。复杂文件、库或持久任务继续使用 Work 沙箱。

## 8. 记忆提取、整理与成本

- 参考 Mem0 的增量候选提取、上下文自足与相关记忆匹配；用户明确的长期协作偏好可以记录，临时任务、外部材料指令及未确认的助手建议不能冒充用户事实。保留证据、时间、作用域和用户删除约束。
- 自动整理按可恢复的有限批次消费未处理内容；旧对话追加只处理新消息和必要前文，已完成内容不重复扫描。失败、重试、编辑、分支、删除、长消息分段及项目隔离遵守通用指南；模型调用不持数据库/用户锁，提交时重新校验。
- 调整当前按自然日一次的限制：用户可对新待处理内容立即整理；并发任务避免重复处理，空结果不阻挡后续新内容。自动整理和已有记忆的去重/过时整理须明确范围及资源预算。
- 用户可查看每次处理范围、候选、过滤/重复原因、实际新增、更新/失效、待处理及失败状态；无变更和原因未知应诚实区分。保留编辑、删除、历史及撤销；不得因整理悄悄恢复用户删除的记忆。
- 全部模型调用遵守[增量记忆与前缀缓存设计指南](2026-10-30-incremental-memory-prompt-cache-guide.md)：固定前缀稳定、动态内容靠后、尽量追加，权限与正确性优先；按真实供应商 usage 评估缓存和 token 成本。

## 9. 验收场景与待定事项

| 范围 | 核心验收 |
| --- | --- |
| 办公技能 | 四种基础技能不可关闭；关闭所有可选技能后 Chat 仍可读取，Work 仍可执行相应办公处理；Chat 不伪称生成、编辑或交付文件；迁移不损用户技能。 |
| 多技能 | 手动选两个技能逐个加载且允许自动发现第三个；Chat 不强制 Work；加载失败明确；全文不在初始提示词预注入。 |
| 输入交互 | 句中多个气泡、斜杠普通文本/无结果、编辑删除/撤销、手机长名称、输入法、技能失效及模板配置均正确。 |
| 提取编辑 | 后台提取不阻塞；可查看、修改、添加/删除草稿文件后确认；多层 ZIP 不丢文件，并发版本和扫描状态正确。 |
| QuickJS | Chat/Work 小计算可用；离线/断线明确；死循环、正则、内存及输出限制有效，测实际设备开销。 |
| 记忆 | 长期偏好、短确认、临时要求、重复/矛盾和删除均按证据处理；旧会话新增内容增量处理；多批次、重试及零结果有解释。 |
| 缓存与导航 | 分供应商实测稳定前缀、追加和失效场景；回到底部按钮不打断主动上滑。 |

待实施设计明确：四个办公技能的精确名称、迁移映射与兼容策略；平台定制交互注册机制；QuickJS 服务端—浏览器协议、无客户端策略与实际资源阈值；记忆重整策略和可观测数据边界。以上是设计问题，不改变已确认的用户目标。
