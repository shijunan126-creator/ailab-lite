# 文件身份、重复上传与自动交付修复方案

状态：2026-11-03已从远端main实施；用户后续授权推送与部署，固定修复分支e05d9a8已部署，详见实施记录。历史数据清理/回填、PR与合并未授权。

## 1. 目标与基线

成功标准是：同一次操作重试不新增文件；同一产物真实修改形成版本；未修改不重复收存；用户明确保存独立副本时保留独立身份；诊断不污染用户资料库；删除、引用、分享、恢复和配额仍有一致语义。数字后缀只用于确有两个独立同名文件的情况，不以隐藏后缀冒充修复。

首次调查基线为 `fix/source-pill-alignment@c033664`，保留既有dirty修改、当时未fetch；后续实施基线为fetch后的 `origin/main@fc63e5f`。实际 API 为 `ailab-local-platform:release-3cd5a61`，镜像 ID `sha256:9b76b72d856aaa8fde696b3729fbb3fb64180775952995c0eb6eb000cf70a201`。调查同时读取运行代码及该发布快照；不能把旧工作树缺少的代码认作现网缺陷。原事件证据入口见[首次诊断](../../progress/updates/2026-11-03-library-duplicate-diagnosis.md)。

## 2. 已核实问题与边界

### 2.1 历史诊断污染是真实直接原因

目标用户会话仅一份原 PPT；五份编号副本分别来自旧后端诊断 Run，另有一份同字节的复现文件。六份都有 `agent.autodeliver`。诊断指令虽说“不交付”，却写入 `/workspace/outputs`，系统兜底自动交付。独立 Run 没有原会话版本父链，因此新建文件再同名避让。不能把它解释为用户会话重复生成或一次 delivery 重投。

### 2.2 重复上传是现有合同，传输重试则存在幂等缺口

普通 `POST /v1/files` 无 parent_id 总新建 FileObject/lineage/upload_provenance；资料库与对话上传入口都没有服务端幂等键。Portal 的上传状态 key 没发给 API。服务端已提交、响应丢失时，浏览器重试能再次创建文件。多次重新选择同一文件也会创建不同条目。已有 `test_library_namespaces.py` 明确要求同名内容保留两份；不能只改断言让它通过。

三份同名 PDF 和另一组两份扫描 PDF 的完整 SHA256 分别相同，每份都有不同上传身份/首次消息。不能据此判断是人工重选还是历史测试。Worker private_copy 缓存只省解析，不去重业务文件。

预签名入口同样每次 presign 新建身份；complete 对已完成请求返回 409，不能在响应丢失后稳定回放成功结果。本机使用本地存储，S3 路径本轮只做源码调查，未真实复现。

### 2.3 新版名称修复有效，但旧记录缺回填

实际发布代码用 `meta.artifact_filename` 保存交付原名，去重和版本父链查询都优先使用它，新版本沿用父文件显示名；已有发布测试覆盖撞名后的多轮版本。

本轮运行代码隔离探针：预先占用 report.txt 后，首次交付显示 report (2).txt；同内容再次提交复用 file_id；修改内容接为 version=2，仍显示 report (2).txt。上一轮基于旧工作树的“当前仍普遍名称耦合”判断在此纠正。

但旧数据没有 artifact_filename 时回退到已加后缀的 filename。移除探针记录该字段模拟升级旧数据，同样原名/内容重提会生成 report (3).txt。只读库存显示有 30 条产物关联查询行缺此字段；不能把查询行数等同于 30 个已发生故障。五个带后缀诊断产物均为这种旧记录。

### 2.4 自动收存会漏更新，也会误回放旧交付

`AgentLoop._deliver_leftovers` 和恢复工作区的基线只记 path→size，没比较内容：同大小覆盖被视为未修改。运行代码的隔离探针中，大小相同的候选没有调用 Broker.commit。

自动交付身份为 run + UUID(path)，不含文件修订身份。一次自动收存后修改同一路径，即使大小变化，再次自动收存仍给相同 delivery_id；API 查到 RunDelivery 直接返回第一次结果。预算暂停/恢复等路径可能多次收存。探针已证明相同身份，API 旧结果返回由真实入口代码确认；本轮未运行完整暂停/恢复故障链。

### 2.5 其他相关边界

- API 交付输入只含 filename，没有源路径身份：不同子目录的同 basename 文件不能可靠区分。应在同次修复明确规则，不能把所有同名当同一产物。
- Docker list_files 当前 find maxdepth=2，按 tab/newline 解析并截到500条，不能代表任意目录完整枚举。此为源码风险，未作为本次重复文件直接原因；修复自动收存时要明确目录和超限合同。
- Broker 注入附件的 _unique_name 只是在沙箱输入目录区分同名附件，不创建资料库文件，应保留。
- 文件移动、恢复碰上真实同名文件时，数字后缀保护两份文件，是正确行为。
- 本轮只读扫描 35 个 live library head，发现3组同用户/项目完整内容重复；未发现同 lineage 多个 head。只读结果是当前小样本快照，非并发/容量证明，不保存原始业务列表进仓库。

## 3. 推荐产品合同

1. **请求重试**：同用户、同操作 id 必须返回同一结果；操作内容不一致则明确拒绝，不能回放旧文件假装成功。
2. **普通再次上传**：默认仅在同用户、同 purpose、同项目、同原始名称、同 MIME、同 size/SHA256 且 READY/live/head 时复用已有文件；返回 reused=true，附件按现有 library 引用语义绑定。不同名称或不同项目不自动归并；技能、模板、品牌资产走原有专用更新合同。
3. **保留独立副本**：资料库提供明确“保存副本”操作，跳过内容复用但仍有操作幂等。正常流程不增加多余说明和确认弹窗。
4. **同名不同内容的普通上传**：保留独立副本并编号；仅明确“更新版本”才绑定 parent。不能用同名推断用户意图。
5. **成果交付**：同会话可见祖先路径上的同一输出槽，内容未变不新增版本；内容变了形成新版本。不同会话/分支上的独立输出不因同 hash 全局归并。分支继承只按可见祖先确定，不改历史文件或把兄弟分支串链。
6. **诊断与兜底**：保留 outputs=交付区的产品合同；诊断中间文件放 work，真实交付验证采用独立测试账号/项目。不要用读取提示词“不交付”来决定系统行为，也不要全局禁用兜底丢失真实成果。

第2条是本方案推荐的产品行为变更，不是现有行为；复用后两个消息引用同一资料库文件，删除该文件会影响两个引用，遵守现有资料库删除传播合同。若要求每次上传独立删除却只显示一项，就需要另做“可见条目与独立附件实体分离”的设计，不能偷偷合并 FileObject 实现。本方案选择既有 library 引用语义，历史引用不重写。

## 4. 实施设计与顺序

### P0：先阻止新的诊断污染

统一真实验收脚本，禁止在用户账号无隔离地创建诊断 Run；中间产物放 work。需要 outputs 行为的验收使用隔离身份，记下准确资源清单；清理由独立 teardown 只处理该清单，不按标题模糊匹配。没有新产品开关、常驻服务或诊断白名单。

### P1：上传操作幂等与重复内容复用

- 新增 UploadReceipt 业务表：user_id + client_upload_id 唯一，保存请求指纹、project/purpose/parent/disposition、结果 file_id、状态及时间。file_id 失效后保留收据墓碑，旧请求返回失效结果，不能复活或重新创建。寿命至少覆盖客户端重试窗口，具体清理策略须在迁移和接口合同中固定。
- Portal 的 lib/uploads.ts 与资料库 uploadFile 共用操作标识规则：首次选择生成，重试保留，显式重新选择生成新标识。请求字段传到 API，响应可丢失但操作身份不变；新上传流程包含幂等键，旧客户端兼容期明确而非永久无键绕过。
- API 流式计算完整 digest 后，在现有用户锁内先查操作收据，再查上述限定候选；安全/配额检查不因复用越权。只复用 READY 且仍可用的文件；pending/rejected/trashed/purged 不作为命中。不把缓存检查代替权限检查。
- 复用不新增 FileObject、不计重复空间、不另排 Worker；本次临时对象删除失败用持久清理意图兜底。新建、收据、outbox 同事务完成；并发相同操作唯一索引兜底。
- 新选同内容撞上 pending 可暂建独立文件，避免把未扫描文件当安全命中；READY 后仅报告重复候选，不后台重写已绑定引用。验收区分“同操作并发幂等”与“不同操作同时上传内容相同”，后者不会被宣称完全去重。
- 每次真正新上传保留独立 upload_provenance。复用返回库引用，不篡改旧文件 first_message_id；引用的 filename_snapshot 取本次可信名称，不能靠修改旧消息修正界面。
- 预签名 presign 同操作复用预约身份；complete 返回并持久化最终 canonical file_id 和完成结果，重试回放；只能在完成后向客户端发布可绑定身份，不能让预约候选提前被消息引用。冻结签名对象再验证 hash/size，保留当前防可复写签名对象合同；过期/无效预约清理有界、幂等。

### P2：修复自动交付内容身份与版本选择

- 保留 artifact_filename 修复，增加 Broker 提供的规范化 outputs 相对路径作为 output_key，API 验证路径形状但所有权仍由 authenticated Run 决定；不要接受模型提供的任意 lineage_id。
- output_key 存在 Artifact 的类型化字段，配合 run_id 索引定位，再经 API 的会话祖先围栏选父链。重命名库文件不改变 output_key；模型显式 filename 只是显示名。源路径改变默认新槽，需要跨路径编辑旧文件时必须用 API 可验证的输入/产物关联，不能靠猜去掉后缀。
- Agent/Broker 将交付/恢复基线改为内容指纹，至少包括 SHA256/size 和可验证来源；mtime/size 只能筛候选，不能证明相同。恢复与压缩只读已保存的交付清单，不重新把未交付改动登记为已交付。
- 自动 delivery_id 绑定 run + output_key + 持久化 revision_id，另冻结该修订的 SHA256。Agent 取得 Broker 内容指纹后，为相对最后确认版本的改动创建 revision_id，先 checkpoint pending intent 再提交，重试复用该 intent；确认后记录结果。不能只用 path+hash 当交付身份：A→B→A 是第三次修订，不能回放第一次A而把B留作head。Broker暂存时重算并核对预期digest，文件在两步间变化则拒绝该旧intent并重新识别，不提交错误内容。明确工具交付仍按已持久化 invocation 身份重试。
- RunDelivery 增加请求指纹（不含随机 staging_key）；同 id 不同内容返回非 fencing 的业务错误（422），拒绝静默旧结果。旧收据缺指纹时依据 file_id/元数据恢复可验证部分，无法验证则拒绝冲突；不把业务冲突返回409导致 Agent误判失去attempt。
- API 先查同操作，再查同 output_key 当前/可见最新版本：同内容复用并在当前 Run 建 Artifact 关联，不新建 FileObject/version；不同内容分配新版本。相同 hash 的不同路径仍独立。旧版本/恢复操作保留明确语义，不以全局 hash 越过 parent。
- checkpoint 持久化指纹、output_key、确认结果；在 API 提交后、Agent checkpoint 前崩溃，重试仍回放同交付；追加消息说明结果，不重写历史消息或工具目录。保持 prefix-cache 合同。
- outputs 枚举返回结构化路径和完整性标记，不能因500条截断/目录深度而静默声称全部交付。限制文件数、总字节、超时；超限给明确未交付结果。文件发生并发修改时以暂存冻结内容为准，停后台写后再收存；不对可变文件做无限重试。

### P3：旧身份修复与历史残留处理

- 先 dry-run：从 API 生成的 storage_key（runs/run_id/file_id/original_name）、Artifact/Run 关系和确认事件恢复 artifact_filename；精确核对路径中的 Run/file 身份，不能一律剥 `(数字)`，否则破坏用户真实名称。这里只补来源元数据，不改原文件字节、id、lineage、历史消息或版本号。
- 新 output_key 缺失的旧记录，只在来源明确时回填；旧 key 常只保留 basename，不能捏造源目录。保留 legacy 名称匹配兼容分支，遇到多候选明确拒绝自动归并并列待处理项。
- 不直接把旧独立 lineage 合并。已有 Artifact、MessageFileRef、RunDelivery、workspace 快照、分享和来源失效传播都有引用，改 FK/删行会破坏历史。
- 已确认的六份诊断输出生成精确清单（原件另列，永不纳入删除）；获得清理授权后使用现有回收站 API，保留可恢复期，不直删对象。若有后续引用，清单展示删除影响并保留；不能把相似标题当诊断身份证明。
- 相同 PDF 只列重复候选，历史独立上传不自动回写引用或删除；需要清理时逐条确认保留哪份，预演来源失效及活动 Run 影响。
- 回填按 id keyset 分批，批次幂等可重入，失败停在可恢复游标；与API写入共享用户锁，SQLite只用安全 ADD COLUMN/新表迁移，PG/SQLite均有upgrade/downgrade。数据来源回填独立于DDL，降级不篡改历史字节。

## 5. 数据库与性能约束

只在真实查询需要处增加 UploadReceipt 唯一索引、Artifact output_key 定位索引、RunDelivery 指纹字段；复用候选先使用现有 ix_files_user_sha，必要时才加 project/purpose 等选择性索引。SQLite/PG 必须用代表性数据做 EXPLAIN，不凭索引名字宣布通过。新的回填/库存扫描 keyset、分批，线上请求不全库读 JSON。

指纹使用传输已有 hash 结果，交付过程不再读一份全文件进内存。自动候选可能需一次有界hash读取，随后暂存流再核对（此为额外I/O，不宣称零开销）；自动收存基线核对是 O(候选总字节)，文件数/字节/期限有界，顺序或单并发；不得每步 hash 整个 workspace，也不增加无限轮询或常驻进程。恢复基线优先采用随 snapshot 保存的清单，旧快照首次补算明确记成本。路径解析/读取继续经过 Broker 限制，覆盖符号链接、路径穿越与超大输出。

目标 API/Broker RSS 不超过当前384MiB限额，Worker不增加常驻负载；以空闲、重复命中、新建、同大小修改、恢复五种场景记录CPU/RSS/磁盘/延迟。预算为既有传输/暂存成本加一次有界内容核对；最终给实测差值，不在方案阶段杜撰耗时。库存仅35个head不代表目标容量已验。

## 6. 集中验收矩阵

| 场景 | 必须满足 |
|---|---|
| 同上传操作响应丢失、并发/重启重试 | 一个结果身份、一个文件、一次队列任务/配额，参数变化明确拒绝 |
| 不同操作同名同内容READY | 默认复用库文件；保存副本才新链；pending策略按上文明确保留 |
| 同名不同内容、跨项目/用户/purpose | 不误合并，不泄露命中信息；新版本仅明确parent |
| 上传检查失败、删除/永久清除后重试 | 不复活、不绕扫描；墓碑语义稳定 |
| S3 presign/complete响应丢失、签名重复PUT | 结果回放、冻结对象不变、不重复收据/任务、无孤儿对象 |
| outputs新文件/无变化/同大小改动/大小变化 | 新增一次/不新增/新版本/新版本，暂停后同路径改动不返回旧交付；A→B→A须生成第三版 |
| 显式交付后兜底、API成功后杀Agent、续跑/压缩 | 一次确认结果，不重复版本，不重复账本，不把未交付文件标为确认 |
| 同名不同子目录、用户重命名、分叉/兄弟分支 | 独立槽位/身份稳定/只继承可见祖先 |
| 旧记录缺artifact_filename/output_key | 精确回填后版本连续；歧义明确报告，原文件/历史引用可读 |
| 移动/恢复/回收站/收藏/分享/来源撤销 | 真实独立文件仍安全避让；复用引用按既有删除合同失效 |
| 诊断与产物扫描边界 | 用户库零诊断写入；超限/嵌套/特殊路径不能静默漏交付 |

先一次性实现相关根因，再集中review/验证；只重跑失败或新变更涉及的项。最终按仓库要求执行 Ruff、完整Python（SQLite及隔离PG/Redis）、Portal test/build、相关真实浏览器E2E；真实模型用隔离身份验证多轮修改/暂停恢复与缓存命中，涉及请求构造则增加 recorded-request 测试和 ≥95% 缓存目标实测，不能用mock替代。Git发布/部署/历史清理只在用户另行授权后执行。

## 7. 实施合同（2026-11-03）

用户已授权从远端最新main实施；基线为 `origin/main@fc63e5f`，隔离分支 `fix/file-identity-repair`。实现及最终验证统一见[实施记录](../../progress/updates/2026-11-03-file-identity-repair.md)，本节取代前文方案阶段的“尚未实施”状态。

- 上传收据保留至账号生命周期结束，不按文件删除清除幂等墓碑；永久删除/版本裁剪会清除收据中的文件名，保留请求摘要及失效身份。API v1兼容不传key的旧客户端，这些请求只有READY内容复用，不能保证PENDING重试幂等；本版Portal普通文件两个入口和个人技能上传全部发送操作key，重试保留。强制key是下一版本接口的破坏性变更，不用任意日期让既有客户端突然失败。
- 原始上传名保存于metadata，收据保存本次可信名称；消息提交携带file→操作key，API核对归属和canonical file_id，再确定upload或library来源。排队消息晋升不重新认领上传来源。保存副本通过独立上传选择入口显式发送copy，不增加说明弹窗。
