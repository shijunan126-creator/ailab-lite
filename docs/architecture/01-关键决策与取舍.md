# 01 · 关键决策与取舍（ADR）

> 每条决策写清楚“选了什么、没选什么、为什么、什么情况下推翻”。调研时间 2026-10，版本状态以当时为准。

---

## ADR-01　模型管理与部署：采用 GPUStack，但只把它当“智算运维面”

**问题**：GPUStack 是否已经覆盖模型管理和部署？

**结论**：覆盖了大约 70%。采用它，但要明确它的边界。

| 能力 | GPUStack 2.x 现状 | 我们的处理 |
|---|---|---|
| 昇腾 910B 纳管、NPU 发现 | ✅ 支持 910B1～B4 / 910C / 310P3，镜像支持 arm64 | 直接用 |
| 推理后端 | ✅ vLLM（vllm-ascend）、SGLang、MindIE、自定义后端；可给内置后端追加自定义镜像版本 | 主用 vLLM；新模型需要的新版本用自定义镜像 |
| 模型来源 | ✅ HuggingFace / ModelScope / 本地路径 | **统一用本地路径**（Pacific NFS），不让 Worker 自己联网下载 |
| 跨机分布式推理 | ⚠️ 标为“实验”；要求各节点模型路径一致 | 只有 DeepSeek（4 机一组）跨机，其余都单机 |
| PD 分离 | ⚠️ 2.2.x 没有；2.3 引入 `vllm-ascend-mooncake` 模式（截至 10-16 仍是 rc） | DeepSeek 1P1D：2.3 GA 前用 vllm-ascend 原生方式部署，GA 后纳入 GPUStack |
| 副本调度 / 路由 | ✅ binpack/spread、手选 NPU、副本数、模型路由（权重分流、fallback） | 直接用 |
| 自动扩缩容 | ❌ 没有按指标扩缩；2.3 有定时扩缩 | 不需要，静态分配 |
| 用户 / SSO | ⚠️ 只有 Admin/User 两种角色；支持 OIDC/SAML/CAS，不支持 LDAP | 只给运维人员登录（经 Keycloak OIDC），最终用户不直接用 GPUStack |
| API Key | ✅ 按用户发放、限定可用模型、设过期；**登录后即可自建 Key**（`POST /v2/api-keys` 只要求已登录） | 只给 Agent Service、文件处理 Worker 各发 1 个服务 Key（限定模型）；因为能登录就能自建 Key，GPUStack 账号只开给 `ops` 组 |
| 限流 / 配额 | ❌ **没有按用户或 Key 的 RPM/TPM/额度** | 由 Higress 和平台补齐 |
| Token 用量 | ✅ 按模型 / 用户 / Key 统计，粒度为天（由它写进 Higress 的统计插件采集） | 用作运维侧总量核对；业务账本在平台 |
| 监控 | ✅ Prometheus 指标 + 内置 Grafana，有 TTFT/ITL/KV 等推理指标和 NPU 利用率/显存 | 接入统一监控；**另外部署 npu-exporter** 采集 HCCS/RoCE/ECC/温度 |
| Server HA | ❌ **单活**，Helm 部署仍是实验状态 | 用外部 HA PostgreSQL，Server 由 K8s 自动重调度（见 06） |

**为什么不自己基于 K8s 加 MindCluster/Volcano 加 vLLM 搭**：可以做到，但等于自己重写一个 GPUStack（模型目录、副本编排、跨机拉起、健康检查、推理指标），运维门槛也高很多。代表处的团队规模下，GPUStack 是性价比最高的选择。

**推翻条件**：GPUStack 在 PoC 中无法稳定拉起所选模型的 vllm-ascend 版本，或者单 Server 的故障影响无法接受。退路是用 K8s + MindCluster device-plugin + 自管 vLLM Deployment 加 Higress 路由（平台其他部分不受影响，因为上层只认网关的模型别名）。

## ADR-02　推理引擎：vLLM + vllm-ascend 插件

**问题**：vLLM 在昇腾上是不是直接用 vLLM 部署？

**答**：**不是直接用原生 vLLM**。昇腾上用的是 `vllm`（上游）加 **`vllm-ascend` 硬件插件**（vllm-project 官方社区项目），依赖 CANN、torch-npu 和驱动固件，版本必须严格配套。实际上不需要自己拼装：
- 官方镜像 `quay.io/ascend/vllm-ascend:<版本>`（不带后缀的是 A2/910B，`-a3` 是 910C，`-openeuler` 是 openEuler 基础镜像）；
- GPUStack 选 vLLM 后端时，会在 910B 节点上自动使用对应的 `gpustack/runner:cann…-vllm…` 镜像。

**选型比较**：

| 引擎 | 结论 | 理由 |
|---|---|---|
| **vllm-ascend** | **主用** | A2 上验证过的模型最多，每个模型都有官方 A2 部署教程（含单机/多机/PD）；OpenAI 兼容；内置 tool-call/reasoning parser；有前缀缓存、MTP、W8A8；Apache-2.0 |
| MindIE | 兜底 | 2025 年底宣布开源，但代码许可证不清晰，二进制要从门户下载；只在某个模型只有 MindIE 能跑时才用 |
| SGLang-Ascend | 备选 | A2 已支持，但 A2 上的模型教程少；某个模型压测明显更优时可以单独用 |
| xLLM（京东） | 不采用 | 社区小，性能数据是厂商自报 |

**注意事项**：
- 910B **不支持 FP8**，量化用 msModelSlim 生成的 **W8A8（默认）** 或 W4A8（大 MoE、需要更多 KV 空间时）；直接用社区（Eco-Tech、vllm-ascend）发布的已量化权重最省事。
- vllm-ascend 迭代很快，**每个模型锁定“镜像 + CANN + 权重版本”组合**，升级要当成一个项目来做（每次升级都用 AISBench 和办公任务评测集回归）。v0.30 已经下线了部分旧模型，模型选型时要看清楚支持状态。

## ADR-03　AI 网关：全平台一套 Higress，GPUStack 以 incluster 模式往里写模型路由

**问题**：GPUStack 2.x 自带网关（就是 Higress），要不要再单独部署一个网关？

**结论**：**只部署一套 Higress**（K8s 里 2 副本 + VIP），既做浏览器入口，也做模型网关；GPUStack 用 `--gateway-mode incluster` 把模型路由直接写进这套 Higress，不再启用它容器里自带的那一套。原因：
1. **这正是 GPUStack 2.x 的标准用法**：GPUStack 的推理请求本来就由 Higress 转发（Higress → Atlas 上的 Worker 代理 → vLLM），GPUStack Server 只负责写路由、管 Key、统计用量。incluster 模式只是把“它自带的 Higress”换成“集群里已有的 Higress”。
2. **自带（embedded）的网关和单副本 Server 在同一个容器里**，Server 一重启推理就中断；用集群里 2 副本的 Higress，网关本身高可用。再配合 GPUStack 2.3 的网关本地鉴权，**Server 宕机时推理不中断**（2.2.x 还做不到，见 02 第 1 节）。
3. **GPUStack 没有按用户限流和配额**：我们在同一套 Higress 上给模型路由加 `ai-token-ratelimit`（按 `x-user-id`），不需要第二层网关。
4. 上层应用只认**稳定的模型名**（如 `ailab-agent`、`ailab-chat`），它们就是 GPUStack 里的模型名或模型路由名；换版本、换引擎在 GPUStack 里完成，应用不改。

> 之前的方案是“自建同步器把实例地址写进 Higress、绕开 GPUStack 网关直连实例”，那是在没有核实 incluster 模式时为解决单点问题想的办法，等于重做了 GPUStack 已有的功能。现在只保留为 P0 不达标时的退路（见 02 第 1 节）。

**备选比较**：

| 网关 | 结论 | 理由 |
|---|---|---|
| **Higress** | **采用** | Apache-2.0，CNCF Sandbox；基于 Envoy，性能和稳定性好；AI 插件齐全（ai-proxy、ai-statistics 按消费者统计 Token、ai-token-ratelimit、ai-quota、key-auth/jwt）；arm64 镜像；同时可以做北向 Ingress（ingress-nginx 已于 2026-03 退役） |
| LiteLLM | 不采用 | 预算/账本 UI 现成，但 **2026-03 发生过 PyPI 供应链投毒**，之后又有未授权 SQL 注入 CVE；管理界面 SSO 超过 5 人要企业版；Python 网关的 CPU 开销较大 |
| Envoy AI Gateway（Agent Router） | 不采用 | 偏 Gateway API 基础设施，没有消费者/Key 管理 |
| APISIX / Kong | 不采用 | Kong 的 Token 限流是企业版功能；APISIX 可行，但团队熟悉度和 AI 生态不如 Higress |

**职责划分**（原则 P6）：
- **网关**（GPUStack 写入的部分）：GPUStack API Key 鉴权、按模型名路由、多实例负载均衡、Token 统计；（我们加的部分）按 `x-user-id` 做 Token 限流（TPM）。**跨模型降级不在网关**：Higress 没有“上游 5xx 就换另一个模型”的插件（2026-10 核实），由 Agent Service 的模型客户端实现（见 09）。
- **平台**：**业务 Token 账本**（精确到用户、部门、会话、Run、模式），额度判定，用量报表。Agent Service 掌握完整的业务上下文，网关做不到这一点。

**风险**：GPUStack 固定使用 Higress 2.1.9，并且独占名为 `default` 的 McpBridge、会写 EnvoyFilter；P0 要验证它和我们的入口路由、限流插件能否共存。不行就给 GPUStack 单独一套 Higress（两层网关）。

## ADR-04　沙箱平台：只用 OpenSandbox，不叠加 agent-sandbox

和对话里最后的结论一致，调研后补充几点：

- OpenSandbox 自带 K8s 控制器（`BatchSandbox` / `Pool` / `SandboxSnapshot` CRD），预热池、过期回收、续期、execd 命令/文件 API、出网控制（DNS 白名单 + nftables 默认拒绝）、Credential Vault 都有，**全部组件都是 amd64+arm64 多架构镜像**。
- `kubernetes-sigs/agent-sandbox` 只是 OpenSandbox 可选的另一种 workload provider，带来的是“K8s SIG 标准 CRD”这一层生态价值，对我们没有实际功能增量。**不加**；以后需要时改一行配置 `workload_provider` 即可切换，上层不用改。

**ARM 支持情况（澄清）**：三者都**正式支持 arm64**，不是“理论上能跑”。

| 组件 | arm64 支持 | 证据 |
|---|---|---|
| OpenSandbox | ✅ | server、controller、execd、egress、ingress、task-executor、image-committer 等镜像都是 amd64+arm64 多架构（已逐个核对镜像清单） |
| Kata Containers | ✅ | 官方支持 aarch64；kata-deploy 4.2 在 arm64 上提供 `kata-qemu` / `qemu-runtime-rs` |
| K8s / containerd | ✅ | arm64 是一等公民 |
| 三者组合 | ⚠️ 没有上游 CI | OpenSandbox 的公开 CI 跑在 x86 上，运行时 e2e 只覆盖 gVisor；arm64 + Kata 的组合要我们自己第一批验证 |

**需要正视的风险**（PoC 中要逐项验证）：

| 风险 | 应对 |
|---|---|
| 项目年轻（1.x 线 2026-09 才发布），**没有 arm64 + Kata 的上游 CI** | P0 用 2～3 周专门验证；锁定版本，镜像同步到内网 |
| Server 单活（Recreate 升级会短暂中断） | Sandbox Broker 对创建请求做重试和排队；已运行的沙箱不受影响 |
| 预热池模板必须固化 runtimeClass、网络策略、卷，不能按请求指定 | 我们本来就是统一模板，不受影响 |
| 暂停/恢复要提交 rootfs 到镜像仓库，耗时数分钟，且不保留内存 | **不使用暂停/恢复**，用“销毁 + 资料库重新注入”代替（原则 P3） |
| 支持的 K8s 版本上限是 1.34 | K8s 锁定 1.34.x |
| 不支持 64K 页内核 | openEuler 22.03/24.03 默认 4K 页，装机时检查 |

## ADR-05　隔离运行时：Kata Containers（QEMU），不用 gVisor 和 runc

- 沙箱里执行的是 LLM 生成的代码，等同于运行不可信代码，必须做到内核级隔离 → microVM。
- **arm64 上 kata-deploy 4.2 只提供 QEMU**（Cloud Hypervisor、Firecracker、Dragonball 只有 amd64）。
- **arm64 上 QEMU 不支持 CPU 热插拔** → 沙箱的 vCPU 数在启动时固定（采用 static sandbox sizing），这也决定了我们只设少数几种固定规格的沙箱。
- **每个沙箱的固定开销**：kata-deploy 默认 PodOverhead 是 **320Mi 内存 + 250m CPU**（arm64 上 QEMU 自身就占 160Mi 以上）。这是容量测算的关键输入，PoC 中实测后可以下调。
- gVisor：arm64 上 syscall 兼容性有缺口，而且和 OpenSandbox 的 `dns+nft` 出网控制、快照都不兼容 → 不采用。
- openEuler 自带的 Kata 版本太旧（24.03 SP2 自带 3.2.0），iSulad + StratoVirt 是另一套生态 → **用 containerd + 上游 kata-deploy 4.x**。
- **Kata 必须跑在裸金属上**：鲲鹏 920 不支持嵌套虚拟化（华为官方 FAQ 确认；ARM 的嵌套虚拟化需要 ARMv8.4 NV2，而鲲鹏 920 是 ARMv8.2），所以 VM 里不能再起 Kata microVM。沙箱节点只能是物理机。

## ADR-06　Agent 运行时：自建 Agent Service（LangGraph + deepagents），DeerFlow 作参考

这是整个平台最核心的一块，备选如下：

| 方案 | 优点 | 致命问题 | 结论 |
|---|---|---|---|
| **A. 采用 DeerFlow 2.1（fork）** | 最接近我们的产品形态：Next.js 界面、Skills、子 Agent、OIDC、RBAC、已内置 OpenSandbox Provider，MIT | ① 上游变化极快（2.1 一个版本合入 772 个 PR），fork 后很难跟进；② 安全设计起点是“本机可信环境”；③ OpenSandbox Provider 才刚加入，产出回传是“尽力而为”且有上限，上传文件不回写；④ 没有部门、额度、资料库配额，这些本来就要自己做；⑤ 官方镜像不是 arm64 | **作参考实现，不作底座** |
| **B. 自建 Agent Service，内核用 LangGraph + deepagents（MIT 库）** | 完全掌控核心契约（会话、Run、沙箱、计量）；deepagents 已经提供规划、文件工具、子 Agent、上下文摘要、Skills 渐进加载；LangGraph 提供 Postgres checkpoint、流式输出、中断与恢复 | 研发量更大（估计 3～5 人月达到可用版本） | **采用** |
| C. AgentScope 2.0（阿里，Apache-2.0） | 原生支持 OpenSandbox，有多租户服务 | 默认示例绑定 DashScope；团队熟悉度低 | 备选（B 方案出现问题时 PoC 对照） |
| D. OpenHands / Suna / OpenManus | — | 企业功能许可受限（PolyForm/ELv2）或已停更 | 不采用 |

**为什么选 B**：
1. 平台差异化在于**和企业体系的集成**（用户、部门、配额、资料库、审计、准入），这部分不管用哪个框架都得自建，占工作量一半以上；
2. Agent 效果主要取决于**模型 + Skills + 工具设计**，这三项都由我们掌握，和框架关系不大；
3. 只依赖库（MIT），不依赖需要商业 License 的 LangGraph Agent Server（Elastic-2.0 / Enterprise Key），也不依赖别人的产品路线。

**沙箱对接**：deepagents 的沙箱后端接口只需要实现 `execute` 和 `upload_files/download_files`。社区已有 `langchain-sandbox-opensandbox`（通过了 86/86 一致性测试），我们**参考它自写约 200～300 行的适配器**，纳入自己的代码库维护。

## ADR-08　身份：Keycloak + 平台内 RBAC

- Keycloak 26.x（Apache-2.0，Operator 部署 2 副本，库放在 CNPG）：负责 AD/LDAP 联邦、OIDC、MFA，并且是 Portal、GPUStack、Grafana、Harbor、OpenSandbox 管理端的统一登录入口。
- **业务权限放在平台内**（部门、角色、配额），不塞进 Keycloak。Keycloak 只同步“用户 + 组”，平台按组映射默认角色。
- 不选 Zitadel（v3 起改为 AGPL）；Casdoor 和 Authentik 也可以，但对 LDAP/AD 和企业的成熟度不如 Keycloak。

## ADR-09　存储协议映射

| 数据 | 存放 | 理由 |
|---|---|---|
| 模型权重 | **Pacific NFS**（`/models`，Atlas 只读挂载，所有节点路径一致） | GPUStack 跨机推理和故障迁移都要求路径一致；只读防止被误改 |
| 用户资料库 | **Pacific S3**（单桶，每个用户一个前缀，开启版本管理） | 天然支持版本、生命周期、预签名直传和下载；沙箱和平台都通过 API 访问，不挂载 |
| PostgreSQL / etcd / Valkey | **TaiShan 本地 NVMe**（CNPG 流复制） | 数据库不放 NFS；Pacific 9950 不提供块存储 |
| 日志（Loki）、镜像仓库（Harbor）、DB 备份 | Pacific S3 | |
| 指标 TSDB | TaiShan 本地盘 | |

**前置确认**：Pacific 的对象（S3）服务是**按服务类型单独授权**的，要先 `show license` 确认。如果没有 S3：资料库改为 **NFS + 每用户一个 dtree 加 20 GB 硬配额**（Huawei CSI 4.7+ 支持），日志和备份改用 NFS。**不用 MinIO**，社区版已停止维护。

## ADR-10　K8s 发行版：kubeadm 原生 1.34

- kubeadm + 上游二进制（不用 openEuler 仓库里的旧 RPM），用 Kubespray 或 oeDeploy 做自动化。
- 不用 KubeSphere（2025-08 开源版停止，4.x 许可证限制商用）；RKE2 可以用，但 openEuler 不在它的支持矩阵里。
- CNI 用 **Calico**（成熟，支持 NetworkPolicy，arm64，和 Kata 的组合经过广泛验证）。
- Ingress 用 Higress（同时做 AI 网关，ingress-nginx 已退役）。

## ADR-11　资源超分：CPU 约 1:3～1:4，内存不超分

- 用 K8s 原生的 `requests/limits` 实现，不需要商业虚拟化或额外的调度器。
- 沙箱：CPU `request 250m / limit 2`（含 Kata 开销后，调度占用约 0.5 核），内存 `request = limit`（Burstable QoS，优先级最低）。
- 平台服务：高 PriorityClass，requests 显式声明；节点有压力时先压缩和驱逐沙箱，平台本身不受影响。
- **三台各 128 核（共 384 核）时 CPU 富余，容量瓶颈在内存**：512 GB/台约 535 个沙箱，约 600 GB/台以上受 CPU 限制（约 620 个）。所以内存配置是决定沙箱规模的关键（见 05）。
- 用负载感知调度（Koordinator）的前提是：同时存在的沙箱超过 300 个，或者实测发现 request 静态浪费明显。本期不上。

## ADR-12　Agent 循环放在沙箱外，沙箱零密钥、默认禁止出网

- 也有方案是在沙箱里直接跑 Codex CLI / Claude Code 这类 CLI Agent。**本期不采用**，否则沙箱里必须放模型 Key、必须能出网访问模型，计量、审计和配额都会失控。
- 我们的沙箱只需要：执行命令、读写文件。出网策略为**默认拒绝**，只放行内网 PyPI/npm 镜像。网页搜索、内部系统 API 等需要网络或凭据的工具，由 Agent Service 在沙箱外执行。
- 以后如果确实需要沙箱访问某个内部 API，使用 OpenSandbox 的 Credential Vault（沙箱里只有假凭据，由出网 sidecar 注入真凭据）。注意它目前是实验特性，有 Host 头匹配的已知问题，上线前要复核。

## ADR-13　模型规划：采纳业务草案，做 3 处可行性调整

**草案**：(a) DeepSeek-V4.1-Flash 4 台 PD 分离，用于复杂 Agent 和 Coding；(b) Qwen3.6-35B-A3B 2 卡 × 10，用于日常办公；(c) 35B 2 卡 × 2，用于识图 OCR；(d) Qwen3.8-27B 4 卡 × 2，用于简单 Agent。合计 64 卡。

**采纳**：(a) 按 **32 卡 1P1D PD 分离**实施（业务方确认可行）：P 放 Atlas-01/02，D 放 Atlas-03/04，KV 经 Mooncake 走 RoCE。设计见 02 第 3.3 节和 [17 图](diagrams/svg/17-deepseek-pd.svg)。

**调整**（详见 02 第 3 节、[04 图](diagrams/svg/04-npu-allocation.svg)）：

| # | 调整 | 原因 |
|---|---|---|
| 1 | (c) 35B × 2 → **DeepSeek-OCR-2 + PaddleOCR-VL 各 1 卡** | 专用 OCR 模型对纯文字和表格识别更准、更省；“看图理解”直接走 (b)（35B 本身是多模态） |
| 2 | (d) TP4 × 2 → **TP2 × 4** | 官方 A2 教程用的是 TP2；4 个实例吞吐更高、故障影响更小 |
| 3 | 新增 **Embedding + Reranker 各 1 卡**；(b) 中 2 个实例兼作**预发槽位** | 资料库检索和 RAG 需要；模型升级需要灰度位置 |

**接受的代价**：DeepSeek 1P1D 只有一组、跨 4 台机器，P 或 D 任一台故障整组不可用，由 Agent Service 自动降级到 27B 兜底。

**推翻条件**：P0 实测发现 V4.1 1P1D 在 A2 上不稳定，或工具调用错误率高（它在昇腾上有过 tool-call 解析 bug），就换成 **DeepSeek-V4-Flash（284B，单机 8 卡 × 4 副本）**。这个方案天然高可用，A2 上也有官方 PD 示例。

## ADR-14　etcd 与控制面：三台 TaiShan 各放一个成员

**背景**：etcd 是 K8s 的状态数据库（Raft 协议，写入需要过半数成员确认），3 个成员能容忍坏 1 个，前提是 3 个成员在 3 台不同的物理机上（见 [03 图](diagrams/svg/03-etcd-quorum.svg)）。

**结论**：通算已确定为 **3 台 TaiShan**，采用 kubeadm stacked 控制面：每台跑 kube-apiserver、scheduler、controller-manager 和一个 etcd 成员，kube-vip 提供 apiserver VIP；三台同时是工作节点（去掉控制面污点）。

| 单台故障 | 结果 |
|---|---|
| 任意一台 TaiShan | etcd 2/3 存活，控制面正常；平台服务由其余节点的副本接管 |
| 同时坏两台 | 失去仲裁；已运行的负载继续跑，按 Runbook 从 etcd 快照恢复 |

**撤销的旧方案**：只有两台通算时，曾比较过“A 新增小管理节点 > B etcd 放 Atlas-01 > C 一台通算起两个 VM”。三台通算后都不需要：智算节点不再跑控制面进程，也不用为 etcd 申请额外机器。堡垒机、出网代理、模型入库主机可以放在公司现有的运维机或 VM 上（可选）。

**注意**：etcd 数据放本地 SSD/NVMe；每节点给系统和控制面预留 8 核 / 32 GB（kubelet `system-reserved` / `kube-reserved`），沙箱的 PriorityClass 最低，避免沙箱把控制面挤垮。

## ADR-15　办公文档生成：模板优先 + HTML 设计 + 视觉自检；沙箱基础镜像 Debian 13

- **PPT**：三条路线混合使用。A 用 python-pptx 填公司母版（默认）；B 让 LLM 写受约束的 HTML，再由 dom-to-pptx 转成可编辑 PPT；C 用 PptxGenJS 直接画。**所有路线都必须渲染成图片，交给多模态模型检查**。Marp、Slidev 导出的是图片页，不作为主路线。
- **Word**：默认用 Markdown + pandoc + 公司 reference.docx；公文用 docxtpl；复杂排版用 docx-js。
- **Excel**：XlsxWriter/openpyxl 写出后，**用 LibreOffice 重算公式并扫描错误值**。
- **基础镜像 Debian 13 arm64**，不用 Ubuntu 24.04：Ubuntu 的 Chromium 只有 snap 包，容器里装不了。
- **许可证红线**：不装 PyMuPDF（AGPL），不用 Anthropic 的文档 Skills（专有）；GPL/AGPL 工具只以子进程方式调用；HarmonyOS Sans 需法务确认。
- 详见 [08-Skills与沙箱环境设计.md](08-Skills与沙箱环境设计.md)。
