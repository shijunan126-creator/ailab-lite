# 项目进度与接续

新 session 从 [当前工作](current.md) 开始，确认现在要做什么、哪些事暂停、下一步是什么，再查相关细节。开发规则见 [AGENTS.md](../../AGENTS.md)。

## 文档分工

| 要回答的问题 | 唯一维护位置 | 更新时机 |
|---|---|---|
| 我们现在在哪、当前授权范围、阻塞和下一步？ | [current.md](current.md) | 任务开始、范围变化、交接前；覆盖旧快照 |
| 下一阶段解决什么、先后依赖、怎样才算通过？ | [roadmap.md](roadmap.md) | 目标、优先级或启动条件变化 |
| T01–T21 各项到底实现到哪里？ | [能力状态矩阵](../architecture/status-matrix.md) | 能力或验收状态变化 |
| 每轮交付了什么、在哪个版本验证？ | [updates/](updates/) 的日期记录 | 每轮交接时追加结果；不复制原始日志 |
| 结论凭什么成立、哪些没测？ | [reviews/](../reviews/) | 审查/验收时保留命令、数据和边界 |
| 后续功能如何实现？ | [architecture/design/](../architecture/design/) | 进入设计或设计变更时 |
| 为什么这样取舍？ | [architecture/adr/](../architecture/adr/) | 形成架构决策时 |
| 哪些坑不能再踩？ | [HANDOFF.MD](../../HANDOFF.MD) | 出现可复用的陷阱时 |

目标架构是 [冻结副本](../architecture/README.md)，不是已实现能力清单。不要用目标文档或旧验收覆盖当前状态。

## 维护约定

- `current.md` 保持简短，只留当前目标、授权/暂停、实际分支/base、最新交付、阻塞、证据入口与下一步。历史详情移入 dated update；不要把 HANDOFF 再复制一遍。
- 沿用 T01–T21 和 F8 编号。新问题写清影响、下一步和验收条件；实际指派后再填负责人/分支，不虚构排期。
- 状态区分“未开始 / 部分实现 / 已实现”“本地验证 / 真实组件验收”和“PR 待合并 / 已合 main”。计划与 Portal 占位不等于端到端能力。
- 每轮 update 写：日期、目标/范围、基线与提交、结果、验证命令和摘要、未验收/阻塞、下一步及 PR 链接。测试数量只描述当时版本，后续结论必须引用对应证据。
- 外部 PR/CI 状态会变化：记录核对日期，接续时从远端重查。未跑、跳过、等待维护者操作分别写清，不能统称通过。
- 用户最新指令优先。当前“剩余功能先暂停”持续生效，直到用户明确恢复；文档维护不自动授权路线图实施。
