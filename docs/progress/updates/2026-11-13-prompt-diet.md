# 提示词瘦身与按需工具：实施与真实模型对比（2026-11-13）

- 用户要求：在效果不变的前提下，压缩提示词和工具说明，减少整体 token；低频工具做成按需加载（Tool Search 思路），常用工具和常用 GenUI 组件直接常驻。必须用真实模型量化首请求和整个任务的消耗，并对比质量。
- PR #197，base `main@e7737c2f`，合并为 `main@6930d3d1`。设计见[提示词瘦身设计](../../architecture/design/2026-11-13-prompt-diet.md)，决定见 [ADR 0043](../../architecture/adr/0043-on-demand-tools.md)。

## 做了什么

- 按需工具 `call_tool`（`agent/deferred.py`）：Work 声明 15 个工具、按需 14 个；Chat 声明 7 个、按需 7 个。第一次用某个按需工具先读说明，再执行；历史保留 `call_tool` 原样，执行、事件和工具日志都用真实工具名。
- 参数 schema 精简（`agent/tool_schema.py`）：文档三件套各从约 1.1k 降到约 0.7k，OCR 从 477 降到 316。
- 系统提示词：两种模式去重、压缩措辞。记忆的改行规则和“记什么”标准、技能保存约定，移到对应按需工具的说明里。
- GenUI 索引：常驻组件去掉 Segments、Steps（212 个回答里各只用过 2 次），措辞压缩，3,306 → 2,789。
- 场景套件新增 6 个场景：图表、联网引用、日期、定时任务、记忆存删、图片识别。报告记录 run_id、输出 token 和回答原文（回答原文写在仓库外）。

## 怎么测的

- 本机测试栈，DeepSeek V4.1 Flash（经 OpenCode Go），同一套 16 个场景、22 个轮次。基线为 `release-e7737c2`（即 `main@e7737c2f`），改后为 `diet-c97783a`；改后只多了一个测试断言修正和文档，见下。
- 样本数：Chat 场景每版各 2 轮；Work 场景（7 个）每版各 4 轮。逐次调用的 token 和计费额取自账本 `model_usage`，按 run_id 汇总。每个场景/轮次取中位数，再求和。计费额为账本 `weighted_amount` 除以 1000，即额度使用的加权 token。
- 复现：`platform/scenarios/token_report.py`（用法见文件开头）。报告和账本导出放在仓库外。
- 基线第 2 轮有 4 个场景被账号的每日额度（默认 200 万加权 token）暂停。调高额度后补跑了这 4 个，被暂停的 run 不计入统计。

## 结果

| 指标（中位数之和） | 改前 | 改后 | 变化 |
|---|---|---|---|
| 首请求 prompt（22 个场景/轮次） | 251,979 | 169,064 | −33% |
| 单次调用平均 prompt，Chat | 11,167 | 7,287 | −35% |
| Chat 整个任务 prompt | 217,754 | 167,604 | −23% |
| Chat 计费额（加权 token） | 87.7k | 71.6k | −18% |
| Work 整个任务 prompt | 2,543,566 | 1,950,882 | −23% |
| Work 未命中缓存 | 217,653 | 169,933 | −22% |
| Work 计费额（加权 token） | 484.7k | 385.6k | −20% |
| 模型调用次数（全部） | 104 | 108 | +4 |
| run 成功 | 62/62 | 62/62 | — |

- 单个新对话的首请求约 1.08 万降到约 0.67 万（Chat）/ 0.78 万（Work）。这一部分在新对话里全部按未命中计费（网关按会话缓存）。
- 多出的 4 次调用都来自按需工具第一次读说明：记忆、定时各 1 次，PPT 里用 `search_images` 前 1 次。即使多了这次调用，这两个场景的计费额仍分别下降 42% 和 27%。
- Chat 计费额只降 18%，是因为“今天几号”和联网问题在基线上恰好命中了跨会话缓存，改后没有命中。其余 Chat 场景下降 27%–38%。
- Work 单个任务的调用次数波动很大，同一场景同一版本 9–30 次不等，来自模型路线差异（看图修版、重读技能），与 `call_tool` 无关：Work 办公场景没有出现 `call_tool`。

## 质量

- 场景断言：改前 2 次失败都是测试的日期格式匹配过严（已修）。改后 2 次失败：一次中文 PDF 用了 Type3 字体，这种字体的字形本来就画在文件里，是测试误判（已修）；另一次 Word 周报没有逐字使用标题《第46周项目周报》，拆成了“项目周报 / 第 46 周”，属于真实的质量失误。同一场景的另外 3 次和基线 4 次都使用了原标题，判断为单次波动，未据此改提示词。
- 逐条阅读 Chat 回答（图表、联网、附件追问、多轮推算）：结论和数据一致，引用格式正确。图表都用了折线图加 Metric，并使用用户原数。改后联网回答有一次主动注明某条来源“仅来自搜索摘要”，符合要求。
- 记忆：两轮都保存成功，并在下一轮按要求删除。定时任务：两轮都按工作日 9:00 创建。

## 测试

- ruff 通过；本机 Python 全量（SQLite）一次，并修正了 14 个按旧措辞断言的测试；新增 `tests/test_deferred_tools.py`（9 项：前缀逐字节扩展、先读后执行、伪造标记无效、非法参数不致 Run 失败、搜索能找到按需工具、schema 精简）。Portal 302 项通过。
- 独立审查（Codex）发现 3 个 P2，均已修复并补回归：`name` 类型错误导致 Run 失败、其他工具结果可伪造“已读说明”、记忆场景失败会残留测试记忆。

## 未覆盖 / 风险

- 样本量有限：Work 每组 4 个、Chat 每组 2 个；未命中缓存的数受跨会话缓存命中的运气影响。
- 没有覆盖的路径：子任务经 `call_tool` 调用按需工具，以及上下文压缩后重新读取说明（只有单元级覆盖）；未声明的按需工具名被直接调用时会直接执行（授权不受影响）。
- Portal 新增了步骤标签“查看工具用法”，未做浏览器检查；本机测试部署也没有重建 Portal。
- 每个模式会有一次预期的前缀重建（提示词版本和工具目录都变了）。
