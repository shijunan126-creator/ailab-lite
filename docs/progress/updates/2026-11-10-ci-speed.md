# CI 与测试耗时（2026-11-10）

分支 `ci/faster-tests`，base `origin/main@37850623`，[PR #176](https://github.com/shijunan126-creator/ailab-lite/pull/176)。只改 CI、测试夹具和测试依赖，未改产品代码，未部署。

## 问题与根因

改动前的 CI 墙钟约 20 分钟，取决于最慢的三个 job（`main@37850623` 之前最近三次成功运行）：

| job | 耗时 | 根因 |
|---|---|---|
| python (sqlite + coverage) | 14.6–17.1 分钟 | 约 2960 个用例串行，一个都不大（最慢 34 秒，>2 秒的只有 41 个）；runner 有 4 核只用了 1 核 |
| python (postgres) | 15.2–19.8 分钟 | 同上，已贴近 20 分钟上限（PR172 曾被取消） |
| e2e | 16.7–19.9 分钟 | 约 3 分钟 Portal 单测与 build，然后约 200 个浏览器用例在一个 stack 上串行跑 |

用例本身是在等待，不是在计算。本机串行全套 11:21，CPU 利用率只有 55%。逐用例对比墙钟与 CPU 时间后找到这些等待：

- 测试 HTTP 服务器 `shutdown()` 要等 `serve_forever` 默认 0.5 秒的轮询，每用一次服务器就多 0.5 秒（`test_prefix_cache` 145 个用例，CI 共 87 秒）。
- LLM 重试退避用默认 1 秒指数退避真睡（`test_gateway_timeout…` 10 秒，`test_failure_before_connect…` 4 秒）。
- 只影响本机：开了系统代理的 macOS 上，httpx 访问 `127.0.0.1` 也走代理，每次请求多 0.2–0.5 秒，`test_prefix_cache` 本机要 3:17。

另外查到一项检查实际上没起作用：`lock_deps.sh --check` 的正则匹配 0 行，所以永远报“consistent”，`defusedxml` 也因此从未写进 constraints。

## 改动

- Python：引入 `pytest-xdist`（CI `-n auto --dist worksteal`）。`tests/conftest.py` 给每个 worker 分配独立的临时目录/SQLite、`<库>_gwN` PostgreSQL 库和独立 Redis db。CI 的 PG 服务关闭 fsync 等持久化选项。job 上限从 20 分钟降到 15 分钟。
- E2E：用 `AILAB_E2E_SHARD=k/3` 按用例 id 哈希分成 3 片，每片自建 stack；Portal 单测从 stack fixture 移到第 1 片的独立步骤，只跑一次。每片上限 15 分钟。
- 测试等待：测试服务器 `poll_interval=0.01`；测试默认 `AILAB_LLM_RETRY_BACKOFF_SECONDS=0.001`；回环地址加进 `NO_PROXY`。
- 依赖：修正 `lock_deps.sh` 正则，补上 `defusedxml`、`pytest-xdist`、`execnet` 的固定版本。

没有删除任何用例和断言，覆盖率门槛（80%）和 `verify_junit` 必须执行的组都不变。

## 验证（本轮，代码基线为本分支）

- 本机 SQLite 串行 11:21 → `-n 8` 91 秒，全部通过。`-n 4` 加 coverage 192 秒，覆盖率 83.24%，Redis 必需组通过。
- 本机一次性 PG16 + Redis 用 `-n 4` 跑 185 秒，全部通过；`verify_junit` 的 Redis/PG 数据库/账本/备份/迁移必需组都实际执行；跳过数 70 ≤ CI 串行的 86，没有新增跳过的用例；各 worker 库 `ailab_test_gw0..3`、`ailab_migrations_gw0..3` 均已建立。
- `test_prefix_cache.py` 本机 3:17 → 约 10 秒。
- `lock_deps.sh --check` 对新 constraints 报 consistent，对旧 constraints 报 out of date。
- ruff、`.github/tests` 28 项、shellcheck 通过；actionlint 由 CI shell job 检查。
- CI 实测（`533ae0cd`，11 项全绿，整轮 12.2 分钟，改动前约 17–20 分钟）：

| job | 改动前 | 改动后 |
|---|---|---|
| python (sqlite + coverage) | 14.6–17.1 分钟 | 7.0 分钟（测试步骤 6.0） |
| python (postgres) | 15.2–19.8 分钟 | 7.3 分钟（测试步骤 6.3） |
| e2e | 16.7–19.9 分钟 | 三片 6.5 / 6.9 / 11.3 分钟 |

  三片 E2E 分别执行 74/64/71 个用例，合计 209、无重复，跳过合计 15，与分片前相同。第 3 片多出的时间里，有 3.8 分钟花在 apt 安装 Chromium/LibreOffice 上（其他两片 0.8–0.9 分钟），属于镜像源波动，不是用例本身变慢。

## 并行暴露的时序断言

只改文档的 `98bf9d0e` 上，python (postgres) 失败了 1 项：`test_500_turn_first_page_is_bounded_and_fast` 断言 100 次请求的墙钟 p95 < 150ms，实测 157ms（同一提交的其他 2874 项通过）。4 个 worker 共用 CPU 和同一个 PG 服务，这个数字测到的是相邻 worker 的负载，而不是这个接口。改为确定性检查：一次请求只加载当页的 `Run` 行（20 个，活跃叶子在页外时 21 个），500 轮路径只按 id 走；延迟仍打印，但不再断言。变异验证：把查询改成加载整条路径时，新断言报 `500 <= 21` 失败；原来的计时断言很可能发现不了这个回归（500 行加载得很快）。仓库里其余计时断言都是“没有被整段 sleep 阻塞”这种有 5 倍以上余量的检查，或者本身就是租约合同（心跳必须在租约到期前停止），保持不变。

## 风险与边界

- 并行会暴露依赖全局状态的测试（整库计数、固定端口），本轮全套在两种库上都没有出现，偶发问题留给后续 CI 观察。
- E2E 分片按哈希划分，三片的耗时不完全均衡；每片重复约 4 分钟的安装和 Portal build，runner 分钟数增加，但墙钟时间减少。
- 只在本机用 `-n 4/8` 验证过 PG；CI runner 的核数按 `auto` 取。
