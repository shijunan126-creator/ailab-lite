# 2026-10-29 对话附件标签预览与解析触发梳理

## 范围和基线

用户要求解释实际文件处理路径，并修复对话中自己发送的附件打开全屏查看器的问题。工作树 `.worktrees/file-context-ocr`，分支 `feat/file-context-office-runtime`，HEAD/base `e71a60f8b4e0ea139b12be80d14cb38a627a2db7` 加已有未提交文件上下文实现。保留全部原改动；不切分支、不push/PR/merge。此前本机部署授权持续有效，本轮只更新Portal组件。

## 当前解析触发（实际代码，不代表完整设计均已验收）

| 文件/用途 | 触发及实际行为 |
| --- | --- |
| PDF、DOCX、XLSX、PPTX上传 | Worker先扫描；匹配同用户内容/解析器指纹可复用私有派生结果，否则由Broker专用系统reader沙箱运行固定ZCode核心，提取正文、结构单元及来源索引。超过资源上限/失败会保留明确状态。Chat/Work/资料库上传均如此。 |
| XLSM、CSV/TSV、文本/Markdown/代码上传 | 隔离的旧解析路径；XLSM为Python表格提取，文本类按编码解码。不是所有能预览的格式都有完整正文提取能力。 |
| 图片上传 | 生成显示图/缩略图，不因上传自动OCR。 |
| Chat发送文件 | 复用已准备正文；PDF清单缺文字的页按需申请OCR，完成后才准入。检查完整性及模型输入预算，超限要求选择范围/切Work，不以截断前缀冒充全文。当前保护值是200000字符、最多200个无文字单元，OCR每批最多20页；这些是当前实现限制，不是已验证模型容量。 |
| Chat/Work发送独立图片 | 根据服务端capabilities：视觉模型直接读图，非视觉模型先OCR文字；不按模型名猜。输入框每轮5张独立图片限制不等于历史/文档页/模型请求上限。 |
| Work使用文件 | 默认给文件引用与索引，模型按任务调用内置skills/工具读指定页、范围、查询和游标；常规读取用持久化块，不重新解析。需要视觉/扫描文字或操作原件时再渲染、OCR或注入用户Work沙箱。 |
| 点击文件预览 | 独立显示处理：复用已有预览，否则请求预览任务并轮询。PDF/Word/PPT等走沙箱页渲染；表格走隔离结构化预览；图片/文本使用相应视图。不调用回答模型、不把全文加入模型输入。页式资料库预览当前最多40页；表格有行列显示保护，不能拿预览覆盖冒充全文处理覆盖。 |
| DOC、PPT、XLS及ODF/RTF等旧格式 | 预览转换支持部分格式，但上传正文提取没有现代四格式的相同合同；不能因为能预览就宣称Chat已读到全文。 |
| 重引、切模式、重复上传 | 同file_id使用已有结果并重查预算；同用户相同内容尽量复用派生缓存。不同用户不共享可见授权；派生对象有独立文件命名空间。 |

Word/PPT内嵌图片和图表不因原生文字提取而自动全部看图/OCR；需要视觉细节时由Work按需渲染读取，当前独立OCR入口只接受PDF和图片。原生正文提取、显示渲染、OCR和模型输入是四个不同阶段；处理范围、缓存覆盖和一次模型输入范围也不同。上传路径是 `worker/pipeline.py`、`worker/office.py`，准入为 `api/attachment_input.py`，预览分类及执行为 `contracts/file_preview.py`、`worker/preview.py`。OCR只计量，不计费；本机显式CPU，真实Ascend/CANN仍未验。按需读取不等于上传时完全不做预处理。

## 修复

共同根因是Turn附件按钮直接调用资料库全屏shell。改为交给Chat的PreviewPane：上传附件以 `file:<file_id>` 作为标签身份，保留真实文件名；同文件重复点选复用标签，同名不同ID分别打开。现有生成文件实时预览路径保留；资料库独立全屏查看器保留。提取共享 `FilePreviewBody`，直接复用现有PDF/Word页、表格、图片及文本渲染，取消过期详情请求；不新增解析器或后端解析入口。侧栏提供下载、切换、关闭、收起及Escape退出；手机沿用带标签的全屏侧栏布局。
